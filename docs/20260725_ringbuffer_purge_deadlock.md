# 2026-07-25 TS リングバッファのパージで受信が停止する不具合

長時間の実機ストレス試験で、選局を繰り返していた受信機の TS が永久に停止する現象を捕捉しました。  
原因は `RingBuffer::Purge()` と読み書きの間にある2つの競合で、いずれも2021年からある WinUSB 版固有の問題です。  
この記録は、現象の観測、原因の特定、修正、検証の順にまとめたものです。

## 観測された現象

PX-W3U4 で選局往復ストレス (2秒受信して切り替えるのを繰り返す) を実行中、366周期目でプロセスが完全に停止しました。  
同時刻に PX-MLT5PE と DTV02A-1T1S-U で走っていた5プロセスは正常に動作を続けています。

停止したプロセスの状態です。

- 30秒間の CPU 消費が 0.00 秒、2スレッドとも同期オブジェクト待ち
- 345周期目から20周期にわたり TS が1パケットも届かず、その間も信号レベルは 32.9 と正常値を取得できていた
- DriverHost_PX4 のスレッド数は変化せず、別の受信機では新規接続と選局が正常に完了した

TS のバルク転送だけが停止し、USB 制御転送は生きている状態です。

## 原因

### 通知の取りこぼしによる待機の固着

`RingBuffer::Purge()` は退避要求 `wait_` を立て、`wait_lock_` を保持して利用者数 `rw_count_` が0になるまで待ちます。  
一方 `Read()` と `Write()` は、利用者数を減らして0になったときに、**`wait_lock_` を取らずに** `wait_cond_.notify_all()` を呼んでいました。

`std::condition_variable` は条件を確かめてから待機列へ登録します。  
このため、`Purge()` が条件を確かめて「まだ利用者がいる」と判断した後、待機列へ登録するまでの間に最後の利用者が抜けて通知すると、その通知は誰にも届きません。  
そして `wait_` が立っている間は `Read()` と `Write()` が即座に戻るため、以後どのスレッドも通知を発行せず、`Purge()` は永久に戻りません。

Linux 版の同じ処理は `wait_event()` を使っており、待機列へ登録してから条件を確かめる順序のためこの穴がありません。  
`std::condition_variable` への移植で確認と登録の順序が逆になったにもかかわらず、通知側の同期が伴わなかったことが原因です。

この固着が観測された現象をすべて説明します。  
ストリームサーバーのワーカーがパージの中で止まるため、そのクライアントからの命令を読まなくなり、`wait_` が立ったままなので TS の書き込みもすべて空振りします。  
クライアントは選局のたびにパージ命令を書き込み続け、名前付きパイプの入力バッファ512バイトが埋まった時点で書き込みがブロックします。  
TS が止まってからクライアントが停止するまで20周期を要したことも、この容量と一致します。

### 初期化と読み書きの競合

`Read()` と `Write()` は `wait_` を確かめてから `rw_count_` を増やしていました。  
確認から加算までの間に `Purge()` が利用者数0を観測して `Reset()` を終えると、初期化前の位置と残量を使って読み書きが進みます。  
`actual_size_ -= read_size` が桁借りして巨大な値になり、次の `Write()` が算出する書き込み長も巨大になるため、確保領域を超えた複製で異常終了します。

こちらは通知の固着を修正して初めて表面化しました。  
固着していた間はパージが完了しないため、初期化と読み書きが重なる状況自体が起きなかったためです。

## 修正

通知は `wait_lock_` を取ってから発行し、確認と待機の間に通知が消えないようにしました。  
また利用者数の加算を先に行い、その後で退避要求を確かめる順序へ変更しました。  
`rw_count_` と `wait_` はいずれも逐次一貫な原子変数のため、この順序であれば `Purge()` と読み書きの少なくとも一方が相手の更新を必ず観測します。

読み書きの通常経路にロックは増えていません。  
`wait_lock_` を取るのは、利用者数が0になり、かつ退避要求が立っているときだけです。

## 検証

`winusb/tests/ringbuffer_purge_test.cpp` を追加し、ソリューションと `build.ps1` へ組み込みました。  
読み出しと書き込みを絶えず往復させながらパージを繰り返し、パージの回数が進まなくなった時点で失敗と判定します。  
毎回のビルドを止めない長さとして、試験時間は10秒にしています。

修正前のコードでは **5回から13回のパージで停止**し、試験が失敗します。  
修正後は10秒間で x64 が2779万回、x86 が1377万回のパージを完走し、停止も異常終了も起きませんでした。  
試験時間を30秒にして測った際は、x64 が1億5817万回、x86 が8017万回でした。

実機での発生率が約2300回のパージに1件だったのに対し、この試験は読み書きを隙間なく回して危険窓を広げているため、5回から13回に1件まで発生率が上がります。  
修正が無効であれば1377万回のパージに対して百万件規模の停止が期待されるところ、観測は0件です。

あわせて、修正を含むビルドで次を確認しています。

- x86 と x64 の `Release-static` ビルドが 0 エラー
- `smart_card_state_test` と `ts_sync_condition_test` が両アーキテクチャで成功
- 修正前のコードへ戻すと `build.ps1` が試験の失敗でビルドを中止する

## 影響範囲と経緯

`Purge()` と通知の実装は、2021-07-17 のコミット `df8bbdc` (原著者 nns779 氏) で追加されたものです。  
以後は改行コードと文字コードの統一以外の変更が入っておらず、2026-07-12 以降の改修はこのファイルに触れていません。

実運用では選局のたびにパージが走ります。  
発生には、パージが待機へ入る瞬間と最後の利用者が抜ける瞬間が重なる必要があり、確率は低いものの、長時間の運用では起こり得ます。  
発生すると当該受信機の TS が永久に停止し、録画中であれば以降のデータがすべて失われます。

回復はアプリケーションの再起動では済みません。  
パージで止まったワーカーは名前付きパイプではなく `Purge()` の中で待っているため、クライアントが終了しても接続が解放されず、DriverHost_PX4 は接続数が0にならないので終了条件を満たしません。  
今回の試験でも、停止したクライアントを終了させてから15分以上経過しても DriverHost_PX4 は動作を続けていました。  
その受信機は他のアプリケーションからも使えないままになり、DriverHost_PX4 を強制終了する以外に回復手段がありません。

## Linux 版への横展開

Linux 版 (`driver/ringbuffer.c`) には、受信を続けたままバッファを初期化する操作そのものがありません。  
`ringbuffer_reset()`、`ringbuffer_alloc()`、`ringbuffer_free()` はいずれも冒頭で `state` を確認し、動作中であれば `-EBUSY` を返して何もしません。  
初期化が走るのは受信が停止している状態に限られるため、読み書きと重なる状況が生じません。

待機の仕組み自体も、Linux 版は `wait_event()` を使っており、待機列へ登録してから条件を確かめる順序のため通知を取りこぼしません。  
受信中のパージは WinUSB 版が選局時のために追加した処理であり、今回の2つの競合はその処理に固有です。  
このため、対応する変更は Linux 版には不要です。
