# 2026-07-25 push 前レビューの記録

この文書は、2026-07-12 以降の WinUSB 版大規模改修 (未 push 27コミット、25ファイル) に対して push 前に実施した多層レビューの結果を記録したものです。  
発見して修正した問題に加え、検証の結果棄却した指摘とその根拠を残します。  
同じ箇所への指摘が将来のレビューで再演された場合は、まずこの記録の棄却根拠と突き合わせてください。

検証環境は Windows 11 上の Visual Studio 2022 (v143) で、実機は PX-MLT5PE、PX-W3U4、DTV02A-1T1S-U (ISDB2056) の3機種です。  
PX-Q3U4 と PX-Q3PE4 の実機はこの環境に存在しないため、2基連動の電源経路は静的検証に留まります。

## レビューの体制

観点を分けた複数の LLM レビュアーによる並行レビューと、別系統の LLM (Codex、CodeRabbit) による独立レビューを突き合わせ、すべての指摘を現行コードと実測で裏取りしてから採否を決めました。  
検証の柱は次の3つです。

- 旧コード (`origin/develop`) との状態遷移の全列挙比較 (退行の検出)
- 自動試験の陽性対照 (修正や検査を意図的に外し、試験が実際に落ちることの確認)
- 実機3機種での測定 (選局往復の TS 混入、APDU 失敗数)

## 発見して修正した問題

いずれも今回の改修が持ち込んだものではなく、以前から存在した問題です。

### 接続待ちの取り消し漏れ (bee50f6)

`PipeServer::Accept()` は `ConnectNamedPipe()` の待機を終了イベントで中断した際、`CancelIoEx()` と完了待ちを行わずにハンドルを閉じて戻っていました。  
カーネル側の処理が残ったままスタック上の `OVERLAPPED` が解放されるため、シャットダウン時に解放済みスタックへの書き込みが起こり得ます。  
読み書き側 (`Pipe::Read()` / `Write()`) には同種の修正が先に入っており、接続待ち側だけが適用から漏れていました。

### データパイプの受信長未検証 (f472fbc)

`StreamConnection::Worker()` だけが受信長を確かめずに `DataCmd` として解釈していました。  
制御パイプとカードパイプには同じ検査が既にあり、対称の最小検査を追加しました。

### 選局試験が通常経路を測っていなかった (a70f5aa)

`BonDriver::SetChannel()` は選局後に内部で `PurgeTsStream()` まで行うのに、試験側でも追加のパージを行っていたため、二重パージ後の結果しか測れていませんでした。  
また選局後に TS が完全に止まる退行が混入0のまま成功扱いになる穴と、PID の収集側と測定側で走査条件がずれ得る作りも同時に直しました。

### 遅延した重複応答の回復試験 (7b7adb4)

後述の棄却判断を回帰試験として固定したものです。

## 棄却した指摘と根拠

### 「遅延して届く重複カード応答が次の APDU を壊す」

再送の後に遅延した古い応答が UART FIFO へ残ると、既存の読み捨て処理 (`DiscardPendingCardData()`) では捨てられず、次の APDU の先頭で読まれます。ここまでは指摘のとおりです。  
ただし直前の応答の受理で受信連番が進んでいるため、残った応答の連番は構造的に必ず不一致となり、`-EPROTO` でセッションが破棄され、次の APDU の再初期化で回復します。  
古い応答が正しい応答として通る経路は存在しません。

提案された「重複を読み切る状態機械」は、カードが重複要求へ必ず応答するとは限らない (EDC エラーなら黙殺し得る) ため確定的に成立せず、明確な失敗と再構築で回復させる現行設計を維持しました。  
この論証は `smart_card_state_test` の残留応答試験として固定してあり、受信連番の検査を外すと該当試験が落ちることを陽性対照で確認済みです。

### 「TS パージの完了が保証されていない」

パイプへ書き込み中のチャンクやパイプ内のカーネルバッファはパージと同期しない、という理論指摘自体は正しい構造です。  
ただし試験を `SetChannel()` 単体の通常経路へ直した上で3機種で再実測した結果、全機種で3周期完走、前チャンネル固有 PID の混入0パケット、空受信0周期でした (各周期2万パケット超を測定)。  
実測で問題が確認できないため、パージの完了応答を待つプロセス間通信プロトコルの追加は見送りました。  
将来この判断を再検討する場合は、まず `channel_purge_test` を対象環境で複数回実行し、混入が再現することを確かめてから設計してください。

### 「2基連動モデルの抜去時に共有ロックを数秒保持する」

USB 抜去時の `SetAvailability(false)` から共有電源管理の `Remove()` を呼ぶ経路で、切断済み USB への電源制御転送が共有ロック下で最大3秒待つ、という指摘がありました。  
`SetBackendPower()` には停止方向かつ `available_` が偽なら即座に戻るガードがあり、`SetAvailability()` は `available_` を偽にしてから `Remove()` を呼ぶ順序のため、この制御転送自体が発生しません。

### 「Linux 版の GPIO2 早期停止が受信中の相方の電源を切る」

`px4_backend_set_power()` の GPIO2 と GPIO7 は各 USB サブデバイス自身の IT930x レジスタであり、片側への書き込みが相方のレジスタを直接変えることはありません。  
初期化時の無条件 GPIO2 停止の後、相方が電源連動を要求していれば `px4_mldev_add()` が正規の手順で再通電します。  
この変更は WinUSB 版で先に実装済みの「共有管理への登録前に基板電源を既知の停止状態へ戻す」処理の横展開です。  
ただし PX-Q3U4 / PX-Q3PE4 の実機では、受信中の再接続で基板の共通電源やファンに影響が出ないことを確認できていません ([linux_pending_verification.md](linux_pending_verification.md) を参照)。

## 修正対象外として記録する既知事項

いずれも今回の改修が作ったものではなく、発火条件が狭いか実害がないため、修正せず記録に留めます。

- `Px4Device::Px4Receiver::SetCapture()` 冒頭の `open_` 検査はロック取得前にあり、`Close()` / `Term()` によるハードウェア破棄と理論上交差し得ます。初版から同じ構造で、到達には接続断処理との狭い競合が必要であり、実際の発火は確認されていません。
- クライアントが受信機を閉じないまま USB を抜いた場合、機器の破棄待ちが通知スレッドを止め、他の機器の着脱通知が遅れます。カードリーダー列挙の巻き添えは修正済みで、破棄待ち自体は接続断で解消します。
- T=1 の WTX 処理中に古い WTX ブロックと正当な応答が連結した場合、先頭の古い WTX だけが採用される理論経路があります。カード側が仕様の境界的な挙動を取ることが前提で、発火の根拠は確認されていません。
- カードリーダー一覧の世代番号 (`reader_generation`) はプロセス間通信の応答に載っていますが、現在のクライアントは変更検知に使っていません。実害はなく、削除は通信構造体の変更になるため残しています。

## 提案として残す事項 (未実施)

名前付きパイプの DACL は Everyone へ読み書きを許しており、この権限にはインスタンス作成も含まれるため、DriverHost_PX4 の起動後に別プロセスが同名パイプへ相乗りする経路と、クライアントが接続相手を検証しない経路が残っています。  
`FILE_FLAG_FIRST_PIPE_INSTANCE` で塞いだのは起動時の先取りだけです。  
DACL のログオン SID 限定とクライアント側のサーバー SID 照合で閉じられますが、別ユーザーアカウントで録画アプリケーションを動かす構成を壊し得るため、互換性の判断とセットで検討が必要です。
