## 採否の基準

外部変更は、次の条件を順番に確認しました。  

1. 現行コードにも同じ問題条件が存在するか
2. 変更が返り値、ロック、機器寿命、電源、TS の不変条件と一致するか
3. 現在の `develop` に同等またはより広い修正が入っていないか
4. 実測が対象機種と変更後のコードを使った結果か
5. ブランチ全体を取り込む必要があるか、局所的な知見だけを使うべきか
6. Windows と Linux の共通層へ影響する場合、両方の契約を維持できるか

「別フォークで動いた」は、通信手順が実現可能である根拠になります。  
しかし、長時間の TS 受信、USB 抜去、共有電源、複数クライアント、エラー後の状態破棄まで満たす根拠にはなりません。  

## Issue #36

### 報告内容

[Issue #36](https://github.com/tsukumijima/px4_drv/issues/36) は、PX4 系の USB チューナーを複数接続した際、使用していない筐体も初期化後にアクティブとなり、LED とファンが動き続ける問題を報告しています。  
投稿された修正は、機器初期化後に未使用のチューナー側基板電源を停止し、受信開始時に対象機器だけを再度有効にするものです。  

### 論理的な妥当性

現行コードでは、IT930x の初期化に必要な GPIO 設定を終えた後も、複数チューナー機のチューナー側基板電源を維持していました。  
受信機を開く処理には電源を再取得する経路があるため、未使用状態で停止する変更は既存の電源契約と一致します。  

停止するのはチューナー側基板電源です。  
USB ブリッジの IT930x は給電されたままなので、ファームウェアや USB デバイス自体が消えるという仮説は成り立ちません。  

### 採用した修正

Windows 側は `a28d48e1cf377115313bfbc925579ec231dc4ec8` で、初期化後に基板電源を停止します。  
Linux 側は `ed28d77137f3f61ee3aac2fa3e6467028579f1af` で同じ契約を反映しました。  

Linux の複数インターフェース機器は、`2d96544e1d5ee33479451ac9b2e4553a2e379062` と `5cc2e7b94fa831fa8dc656dba02720daf6bdf097` で共有電源と参照寿命を補強しています。  
カードリーダーを追加する際は、カードも同じ基板電源の利用者として数えます。  

### 検証の限界

Windows 検証環境の3機種では、修正後も通常受信とカード通信が成功しました。  
Issue 投稿者と同じ PX4 系2筐体の構成は用意できず、未使用側の LED とファンを同条件で確認していません。  

Linux 側はビルドと実機確認が残っています。  
このため Issue はクローズせず、コミットメッセージの `(#36)` による関連付けに留めています。  

## Issue #38

### 報告内容

[Issue #38](https://github.com/tsukumijima/px4_drv/issues/38) は、DriverHost_PX4 が動作しているにもかかわらず、BonDriver 側で `no receivers available` となる稀な現象を扱います。  
DriverHost_PX4 を終了すると回復する場合があり、受信機管理、再オープン、USB 列挙、TS 開始失敗のいずれも候補になりました。  

同じ表示は複数の内部失敗を集約するため、報告だけから単一の原因を特定できません。  
現行コードで独立して不正と確認できた箇所を、別々の修正として採用しました。  

### ReceiverManager の GUID 比較と排他

コミット `f108339027ca7aec0ad61c2946af359ec29cd894` は、受信機の GUID を値として比較し、受信機一覧の取得と更新を同じ排他制御へ入れます。  
GUID オブジェクトのアドレスや、保護されていない一覧を比較すると、同じ受信機を見失う可能性があるためです。  

この問題はコード上で成立し、修正範囲も ReceiverManager の識別と一覧保護に限定されます。  
Issue #38 の再現を待たずに直す価値があると判断しました。  

### USB シリアル番号の転送長

コミット `93ab9f2fff4795064568c85fe52c41c55c3e735a` は、USB 文字列記述子を固定バッファ全体ではなく、WinUSB が返した実際の転送長の範囲で解析します。  
未初期化または以前の内容が残る領域まで文字列として扱うと、機器 ID と複数インターフェース機器の対応付けが不安定になります。  

PX4 系の複数インターフェース判定とカードリーダー名もシリアル番号を使うため、受信機だけに閉じた問題ではありません。  
転送長を信頼境界にする修正を採用しました。  

### BonDriver 再オープン時の終了イベント

コミット `e5ac32d4e9e3e3d772f9d2394897be41e3e01e96` は、BonDriver を一度閉じた後に再度開く際、以前の終了イベントをリセットします。  
終了状態が残ると、新しい受信処理が開始直後に終了条件を満たし、正常な再オープンを妨げます。  

DriverHost_PX4 のプロセスを終了すると回復するという観察と両立しますが、このコミットだけを Issue #38 の唯一の原因とは断定していません。  
イベントの寿命として独立に不正なので採用しました。  

### TS 転送開始失敗の返却

コミット `58d7cc95f17402fff6b0723a4c0b0c91bc6dee3e` は、WinUSB の TS 転送を開始できなかった場合に成功を返さず、確保済み転送を回収して呼び出し元へエラーを返します。  
開始失敗を成功扱いすると、受信機を開けたように見えながら TS が届かない状態を残します。  

`no receivers available` と「開いたが TS が届かない」は表示される層が異なる場合があります。  
それでも、失敗を成功へ変換するコードは明確に修正対象なので採用しました。  

### 採用しなかった仮説

StreamConnection が DataId を解放すべきという案は採用しませんでした。  
DataId の割り当てと解放は制御接続が所有しており、ストリーム接続が同じ識別子を解放すると、制御接続の寿命と競合するためです。  

`open_count > 0 && !init` を通常の休止状態として扱う案も、現行の受信機が休止中も初期化状態を維持し、この組み合わせが通常遷移として作られないことから棄却しました。  

基板電源停止で IT930x のファームウェアが消えるという仮説も、Issue #36 と同じ理由で成り立ちません。  
停止対象はチューナー側基板であり、USB ブリッジは動作を継続します。  

### 残る確認

Windows 検証環境の通常受信と短時間負荷では、修正後の再発を確認していません。  
稀な長期状態は再現できておらず、どの修正が Issue 投稿者の現象へ一致するかは未確定です。  

長期稼働確認は Issue 投稿者へ依頼します。  
各コミットには `(#38)` を付けていますが、完全解決を確認できていない段階なので `Close #38` とは書いていません。  

## PR #2

### 変更の目的

[PR #2](https://github.com/tsukumijima/px4_drv/pull/2) は、PX4 系の地上波受信機で T1 を先に使用した後に T0 を開くと、T1 側へドロップが発生する問題条件を避けるため、通常の受信機選択順を調整します。  
機器内部の干渉を消す変更ではなく、通常利用で危険な順序を選びにくくする変更です。  

### Windows 検証環境での確認

PX-W3U4 の通常設定では、T0 が T1 より先に選ばれました。  
T1 を明示指定してから T0 を開くと、既知のドロップを再現できました。  

後者は PR #2 の選択を迂回した試験なので、PR #2 が無効になった証拠にはなりません。  
通常順序の回避と、ハードウェア干渉が残ることを別々に確認しました。  

### 追加ソートの採否

ReceiverInfo の番号や登録順を明示的な比較キーへ追加すれば、通常順序をコード上で強められます。  
実装量自体は大きくありません。  

しかし、現在の通常構成で T0 先行を実測でき、並べ替えが他機種と明示指定へ影響するため、再現条件のない追加変更は見送りました。  
Linux では `/dev/px4video2` が T0、`/dev/px4video3` が T1 となる現在の対応を維持し、Mirakurun の定義も T0 を先にします。  

## makeding 氏の `linux-with-card-reader`

### 調査対象

[比較ページ](https://github.com/tsukumijima/px4_drv/compare/develop...makeding:px4_drv:linux-with-card-reader) は、Linux 上の PX4 系カードデバイス、PC/SC IFD ハンドラー、ACAS 対応を含みます。  
PX-Q3U4 と ACAS の組み合わせで、B-CAS 互換通信を実際に確認した点が最も価値の高い情報です。  

### 採用する情報

- PX-Q3U4 のカード GPIO と IT930x UART の接続
- TA1 `0x13` と38400bpsの実機条件
- ACAS で IFS を先に送り、必要時に RESYNCH する挙動
- BWI を待機時間へ反映する必要性
- PX-Q3U4 上で Linux のカードデバイスから pcsc-lite まで接続できること
- udev 規則、IFD ハンドラー、pcscd 設定が配布物として必要になること

これらは、Linux 実装の実現可能性と ACAS の実通信を支える外部実測として採用します。  
Windows 側でも、同じ知見を自動試験へ固定しました。  

### 採用しない範囲

一方、現行 `develop` より古い Windows 実装を含み、カーネル側の待機、機器寿命、共有電源、エラー後の状態破棄が現在の契約と一致するか確認できないため、ブランチ全体の取り込みは見送りました。  

Linux 側では、カーネルを物理デバイスと寿命へ限定し、T=1 の状態機械をユーザー空間へ置く構成で再実装します。  
makeding 氏のコードは、レジスタと実機応答を確認する資料として扱います。  

## onpat 氏の派生実装

### 調査対象

[比較ページ](https://github.com/nns779/px4_drv/compare/develop...onpat:px4_drv:develop) は、ISDB2056 系の内蔵カードリーダー、基板電源の利用数、カーネル API 追従を含みます。  
DTV02 系でカード通信を接続した先行実装として参照しました。  

### 採用する情報

- ISDB2056 系のカード初期化位置
- カード利用中に基板電源を維持する必要性
- カード初期化失敗時に取得した電源利用数を戻す必要性
- 機種側から共通 IT930x UART へ接続する方法

これらは Windows 側の ISDB2056 実装と共有電源の契約にも一致します。  
Linux 実装では、機種接続の資料として使います。  

### すでに取り込まれている情報

派生実装に含まれる `strscpy()`、カーネル版に応じた `class_create()`、`module_init()` の修正は、現在の `develop` に相当する対応が既に入っているため、改めて取り込む必要はありません。  

ブランチ全体を移植すると、現在のカーネル互換処理と競合するため、カードと電源に関係する知見だけを採用します。  

## yyya-nico 氏の派生実装

### 調査対象

[比較ページ](https://github.com/tsukumijima/px4_drv/compare/develop...yyya-nico:px4_drv:develop) は、PX4、PXMLT、ISDB2056、PX-M1UR、PX-S1UR へ Linux 内蔵カードリーダーを広げています。  
対応機種が広く、カードスロット、GPIO、デバイス登録位置を調べる資料として価値があります。  

### 採用する情報

- 機種ごとのカードスロット有無
- GPIO と IT930x UART の接続候補
- Linux のプローブと解除へカードデバイスを接続する位置
- PX-M1UR と PX-S1UR を含む機種差の調査起点

個々の値は、現行の `DeviceDefinition`、Windows 側の同機種実装、実機の3者で再確認します。  
派生実装に存在するというだけでは、最終的な根拠にならないためです。  

### 採用しない範囲

一方、大きな IFD ハンドラーとカーネル側カード処理が密に結び付き、絶対期限、抜去後の状態破棄、ACAS、APDU 分割、共有電源、USB 切断時の参照寿命を現在の水準で確認できないため、プロトコル実装と全体構成の基準にはできません。  

Windows 側の内蔵カードリーダー実装は、現在の状態機械、WinSCard API 互換、外付けリーダー共存、実機試験の点で、yyya-nico 氏の実装より Linux の基準に適しています。  
Linux 側は yyya-nico 氏のコードを移植する作業ではなく、機種情報を参照して現在の設計へ接続する作業とします。  

## take1t4u 氏の修正

### 調査対象

[コミット `e9a8d2e8ec614e96c9529e546f9a106e566caef6`](https://github.com/take1t4u/px4_drv/commit/e9a8d2e8ec614e96c9529e546f9a106e566caef6) は、URB エラー処理、エラー戻り値、ロック解放順序を修正します。  
Fable 5 による提案という由来は採否の根拠にせず、現行コードとの対応を個別に確認しました。  

### 採用した内容

WinUSB の TS 転送開始失敗を呼び出し元へ返し、途中まで確保した転送を回収する必要性は妥当です。  
現在の `58d7cc95f17402fff6b0723a4c0b0c91bc6dee3e` は、この条件を現在の WinUSB 実装へ合わせて処理します。  

TS 読み取り引数でビット単位 OR が必要な箇所に論理 OR を使っていた問題は、`e5103cdf373705ab7cf01975c2ccc29ebe850e05` で修正しました。  
Linux の USB ストリーム入力検査と URB 確保失敗時の回収は、`1e1e53a5588feff33d7c70ab9d3df29f6ac4510e` で修正しました。  

### 取り込み方法

外部コミットをそのまま cherry-pick せず、Windows と Linux の現在の API と所有権へ合わせて分けて実装しました。  
現在の WinUSB 側は、開始失敗の返却と確保済み処理の回収を、外部コミットより広い呼び出し関係で扱います。

## soralis0912 氏の実装

[`it930x_driver_native`](https://github.com/soralis0912/it930x_driver_native) は、IT930x UART とカード GPIO の通信手順を確認する資料です。  
公式 BDA ドライバしか利用できなかった機能を、公開コードから再現できることを示した点に価値があります。  

現在の [`it930x_bcas_*()`](../driver/it930x.c) とレジスタ操作を照合する用途に使います。  
現行 Linux カーネルの機器寿命、共有電源、PC/SC 接続、TS 同時負荷を満たす根拠にはならないため、コード全体の移植は対象外です。  

## 調査後の採否

Issue #36 と Issue #38 からは、現行コードでも成立する局所的な修正を採用しました。  
PR #2 は通常選択で有効と確認し、追加の並べ替えは見送りました。  

makeding 氏の派生実装からは PX-Q3U4 と ACAS の外部実測、onpat 氏と yyya-nico 氏の派生実装からは機種接続と電源の情報を採用します。  
各ブランチのプロトコル実装と全体構成は、現在の Windows 状態機械と Linux の推奨分担へ置き換えます。  

take1t4u 氏と nanamitm 氏の変更は、現行コードへ同等またはより広い修正として取り込み済みです。  
2026年7月24日時点で、提示された外部差分から Windows 側へ追加で実装すべき既知の変更は残っていません。
