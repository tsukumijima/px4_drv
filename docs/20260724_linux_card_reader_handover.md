## 現在の到達点

Windows 版の内蔵カードリーダーは、Linux 版の設計元として固定できる状態です。  
Linux 実装に必要なハードウェア操作も [`driver/it930x.c`](../driver/it930x.c) と [`driver/it930x.h`](../driver/it930x.h) に共通処理として入っています。  

Linux 側に残っている主要作業は、次の2系統です。  

1. 現在の `develop` に入っている Linux 向け小規模修正を、対象カーネルでビルドして実機確認すること
2. Linux 版の内蔵カードリーダーを、カーネル側の機器操作とユーザー空間の PC/SC プロトコル処理に分けて実装すること

Windows 側で新たに実装してから Linux へ移すべき既知のカードリーダー修正は残っていません。  
ただし、実際に挿入されていたカードの ATR と選択されたボーレートを記録していないため、Windows 検証環境の実機試験だけから ACAS カードの実通信を証明することはできません。  
ACAS の状態遷移は自動試験済みであり、PX-Q3U4 と ACAS の実通信は後述する makeding 氏の派生実装で報告されています。  

Windows 側で Linux 実装へ直接関係する直近のコミットは次のとおりです。  

- `698861d88508230ed9a877cfba688797116b581a` 内蔵カードリーダーの ACAS 対応と共通 IT930x UART の38400bps対応
- `09836a961612fa6a7f52d30fe66c114cf6e0869e` ACAS の APDU を UART フレーム上限で分割
- `9211e6e2d6250be0dad105e7cbb2cc33e2a3bead` カード状態試験をプロジェクト単体でもビルドできるパスへ修正
- `9eebc4d22b88b2f7cee07bd6bb255ff4901b77ca` 外付けカードリーダー未接続時の試験を明示的にスキップ
- `f1c5a2cb7df824474b884e7a2006cb242baf0939` BonDriver の終了イベントを閉じた後にハンドルを無効化

## Windows 側で確定した設計

### 責務の分割

Windows 版では、カードの物理操作と T=1 プロトコル処理を分離しています。  
Linux 版でも、この境界を維持してください。  

[`winusb/src/DriverHost_PX4/card_device.hpp`](../winusb/src/DriverHost_PX4/card_device.hpp) は、カード検出、リセット、送受信、ボーレート変更を機種実装へ要求するインターフェースです。  
[`winusb/src/DriverHost_PX4/smart_card.cpp`](../winusb/src/DriverHost_PX4/smart_card.cpp) は、ATR 解析、T=1 の状態、再送、タイムアウト、APDU 分割を担当します。  

T=1 の状態機械をカーネルへ置く構成は、次の理由から見送りました。  
カーネル側はカード用デバイスの寿命、排他、共有電源、IT930x UART 操作を担当し、ユーザー空間の PC/SC IFD ハンドラーが ATR と T=1 を担当する構成を推奨します。  

この分割には次の理由があります。  

- T=1 の状態遷移を模擬 I/O で自動試験できること
- WTX や再送による待機を、TS 受信に関係するカーネルロックへ持ち込まずに済むこと
- カーネル更新と独立してプロトコルの修正を配布できること
- カード抜去や USB 切断を、カーネルの機器寿命と PC/SC のセッション状態に分けて扱えること

### ATR と ACAS

ATR の解析は [`SmartCard::ParseAtr()`](../winusb/src/DriverHost_PX4/smart_card.cpp) を基準にします。  
製品コードやカーネルドライバへ B-CAS 固有 ATR の一覧を持ち込まないでください。  
ACAS には B-CAS カード互換機能があるため、カード名の推定より、ATR が示す通信条件を正しく適用することが重要です。  

現在の実装が扱う条件は次のとおりです。  

- 直接規約 `0x3b` と逆規約 `0x3f`
- TA1 の `0x11`、`0x12`、`0x13`
- TA3 が示す IFSC
- TB3 が示す BWI
- TC3 が示す LRC または CRC
- TCK の XOR 検証
- 最大33バイトの ATR と、解析後に余分なバイトを許さない長さ検証

TA1 の `0x13` は38400bpsとして扱います。  
Windows 側では、TA1 が `0x13` のカードを ACAS として扱い、最初に IFS 要求を送ります。  
IFS 要求がタイムアウトか形式エラーになった場合は、RESYNCH の後に IFS を再送します。  

B-CAS では、RESYNCH の後に IFS 要求を送ります。  
この順序差はカードの実際の応答挙動に合わせたものなので、見た目の対称性のために統一せず、現在の [`SmartCard::InitializeT1()`](../winusb/src/DriverHost_PX4/smart_card.cpp) と同じ順序を保ってください。  

### APDU と T=1

T=1 の実装元は [`winusb/src/DriverHost_PX4/smart_card.cpp`](../winusb/src/DriverHost_PX4/smart_card.cpp) です。  
Linux 向けに書き直す際も、次の挙動を契約として維持します。  

- 送信シーケンスと受信シーケンスを、セッションの初期化時にリセット
- カードが提示した IFSC と、UART フレームの上限から算出した INF 上限の小さい方で APDU を分割
- UART フレーム上限は255バイト
- LRC 使用時の INF 上限は251バイト
- CRC 使用時の INF 上限は250バイト
- I-block のチェーン、R-block の応答確認、再送要求を区別
- 最終 I-block の応答を受信できなかった場合に、R-block で応答を回収
- カードから届くチェーン応答を連結し、出力領域不足を明示的なエラーとして返却
- WTX を受理しても、APDU 全体の絶対期限を延長しない
- 通信失敗時は、ATR、連番、CRC、IFSC、タイムアウトを含むセッション状態を一括破棄

ブロック単位の再試行回数は3回です。  
通常のブロック待機時間は500msを下限とし、BWI から `100ms << BWI` を計算して、APDU 全体の3000msを上限にします。  
各再試行で APDU 全体の期限を作り直してはいけません。  

254バイトの APDU を LRC 付きで1ブロックへ格納すると、ヘッダー3バイトと LRC1バイトを合わせて258バイトになり、255バイトの UART 上限を超えます。  
現在の実装はこの入力を拒否せず、251バイトと3バイトへ分割します。  
Linux 側でも同じ分割を行ってください。  

### カード抜去と通信失敗

[`SmartCard::GetStatus()`](../winusb/src/DriverHost_PX4/smart_card.cpp) は、カードの挿入を検出するとセッションを初期化し、抜去を検出すると以前の状態を破棄します。  
[`SmartCard::Transmit()`](../winusb/src/DriverHost_PX4/smart_card.cpp) は、送信前にカードの存在を確認し、未初期化なら初期化します。  
通信エラーを返す場合は、次の要求が古い連番や ATR を再利用しないよう、セッション全体を無効にします。  

ATR が形式不正だった場合に限り、カードリセットを1回だけ再実行します。  
対応外の TA1 は `-EOPNOTSUPP` 相当で明示的に拒否します。  
形式不正、未挿入、USB 切断、時間切れを同じ成功扱いへ変換しないでください。  

## 共通 IT930x 実装

Linux と Windows で共有するカード用ハードウェア操作は、すでに [`driver/it930x.c`](../driver/it930x.c) にあります。  
Linux 側のデバイス実装から、この API をそのまま呼び出してください。  

現在の API は次の処理を提供します。  

- `it930x_bcas_init()` による UART mode 1 とカード検出 GPIO H6 の初期化
- `it930x_bcas_reset_card()` による GPIO H14 のリセット、UART RX の初期化、9600bpsへの復帰
- `it930x_bcas_check_ready()` による受信可能状態の確認
- `it930x_bcas_get_data()` による受信長の取得と最大32バイト単位の読み出し
- `it930x_bcas_send_data()` による最大48バイト単位の送信と、最終チャンク直前の実送信指示
- `it930x_bcas_detect_card()` によるカード検出
- `it930x_bcas_set_baudrate()` による9600bps、19200bps、38400bpsの選択

`it930x_bcas_send_data()` の長さは `u8` であり、1回のフレーム上限は255バイトです。  
38400bpsでは、IT930x UART mode 1 のリロード値 `0xef` を使用します。  
9600bpsと19200bpsで使う既存の設定値も、機種側で再定義しないでください。  

`it930x_bcas_get_data()` は呼び出し側の受信容量を超えないよう検証し、実際の読出長も確認します。  
この境界検証を Linux の上位層で緩めたり、長さが合わない受信を成功扱いにしたりしないでください。  

## 機種別の電源とカードスロット

### PX4 系

Windows 側の実装は [`winusb/src/DriverHost_PX4/px4_device.cpp`](../winusb/src/DriverHost_PX4/px4_device.cpp) を参照してください。  
カードを開くと、チューナーと共有する基板電源の利用数を増やしてから `it930x_bcas_init()` を実行します。  
初期化に失敗した場合は、増やした電源利用数を必ず戻します。  

カードを閉じる処理はカード側の利用数だけを減らします。  
受信機が使用中なら基板電源を維持し、カードだけが使用中の場合も同様に維持します。  
最後の利用者が閉じた場合に限り、チューナー側の基板電源を停止します。  
USB ブリッジの IT930x 自体は給電されたままです。  

PX-W3U4、PX-Q3U4、PX-W3PE4、PX-Q3PE4 のような複数インターフェース機器では、同じ筐体に属するインターフェース間で電源状態を共有します。  
VID `0x0511` の PID `0x084a`、`0x024a`、`0x074a` では、シリアル番号から得る `dev_id == 1` の側だけが物理カードスロットを持ちます。  
同じ筐体にカードデバイスを2つ登録しないでください。  

### PXMLT 系

Windows 側の実装は [`winusb/src/DriverHost_PX4/pxmlt_device.cpp`](../winusb/src/DriverHost_PX4/pxmlt_device.cpp) を参照してください。  
PX-MLT8PE は、5チューナー側と3チューナー側が別の USB デバイスとして見えます。  
コード上の `PXMLT8PE3` は3チューナー側を示し、カードリーダーを持つのは5チューナー側だけです。  

カードと受信機の電源利用数を共有する契約は PX4 系と同じです。  
製品名の近さだけを根拠に、PX4 系の GPIO やインターフェース判定を流用しないでください。  

### ISDB2056 系

Windows 側の実装は [`winusb/src/DriverHost_PX4/isdb2056_device.cpp`](../winusb/src/DriverHost_PX4/isdb2056_device.cpp) を参照してください。  
ISDB2056 系は、同じ IT930x 上で TS と B-CAS UART の制御転送を実行します。  
カード単体の APDU 試験に加え、受信中の APDU を必須試験にします。  

電源を有効にした後のカード初期化に失敗した場合は、カード側が取得した電源利用数を戻します。  
なお、Linux 側の [`driver/isdb2056_device.c`](../driver/isdb2056_device.c) にカード処理はまだ存在せず、コミット `2559c7b34b0739802d5f716152600448aa11a4f9` が修正したのはチューナー open 失敗時の電源解放漏れです。  
カード実装時には、この修正が塞いだものと同じ形の失敗経路がカード側の電源利用数にも生まれるため、同じ考え方で解放漏れを防いでください。  

### Linux 側の機種判定

Linux 側で対応機種を追加する前に、[`driver/px4_usb.c`](../driver/px4_usb.c) の `DeviceDefinition` と各機種のプローブ処理を確認してください。  
Windows 側に存在する機種名を、そのまま Linux 側の別デバイス実装として追加しないでください。  
VID と PID だけからカードスロットの有無を推測せず、現在の機種定義、インターフェース番号、シリアル番号、既存の電源構成を組み合わせて判定します。  

## Linux 側の推奨構成

### カーネル側

カーネル側には、機種共通のカード用文字デバイス層を追加します。  
仮のデバイス名は `/dev/px4cardN` が分かりやすいものの、公開 ABI を確定する前に既存フォークと PC/SC IFD ハンドラーの接続方法を照合してください。  

文字デバイス層が担当する範囲は次のとおりです。  

- 物理カードスロット1つにつきカードデバイス1つを登録
- 1つの UART セッションを守る排他的な open
- カード検出、リセット、ボーレート変更、送受信の機種共通操作
- カード挿抜、受信可能、USB 切断を通知する `poll()`
- カードと受信機で共有する基板電源の利用数
- USB 切断後も開かれているファイル記述子が参照するオブジェクトの寿命
- USB 切断時に待機中の処理を起こし、以後の機器操作へ `-ENODEV` を返す処理

カードを開いている間に USB が切断されても、ファイル記述子が閉じる前にオブジェクトを解放してはいけません。  
プローブ解除時は利用可能状態を無効にし、待機を解除し、ハードウェアへ触れない終了処理へ切り替えます。  
最後の open 参照がなくなった時点で、カード用オブジェクトを解放します。  

カーネルの公開 ABI には固定幅の整数型を使い、32bitユーザー空間との互換性を確認します。  
可変長ポインタを含む独自構造体を安易に `ioctl()` へ渡さず、最大255バイトの送受信長と実際の返却長を明示してください。  
カード未挿入、時間切れ、USB 切断、形式不正を区別できる errno を維持します。  

カード応答を待つ長いポーリングループはユーザー空間へ置きます。  
カーネル側で待機が必要な処理も、USB 切断で中断できることと、TS 受信に関係する広いロックを保持しないことを確認してください。  

### ユーザー空間

ユーザー空間には、pcsc-lite が読み込む IFD ハンドラーと、独立して試験できる T=1 プロトコル実装を追加します。  
プロトコル実装は [`winusb/src/DriverHost_PX4/smart_card.cpp`](../winusb/src/DriverHost_PX4/smart_card.cpp) の状態遷移を移植し、Linux のファイル I/O を薄いアダプターとして接続します。  

IFD ハンドラーは次の処理を担当します。  

- pcsc-lite が要求するリーダーの列挙と open
- ATR の取得と返却
- APDU の送受信
- カード挿抜状態の通知
- PC/SC の共有と排他を、カーネル側の単一 UART セッションへ対応付ける処理
- USB 切断とカード抜去を、pcsc-lite が区別できるエラーへ変換する処理

カーネル側は物理 UART を排他的に開き、複数アプリケーションからの共有は pcscd の上で管理する構成を推奨します。  
各アプリケーションが `/dev/px4cardN` を直接開ける構成にすると、T=1 の連番と再送状態を複数プロセスが破壊するためです。  

外付けカードリーダーは pcsc-lite の既存ドライバに任せます。  
PX4 内蔵リーダーを追加した結果、外付けリーダーの列挙や共有モードが変わらないことも確認してください。  

### ビルドと配布

カーネルモジュール、IFD ハンドラー、pcsc-lite の設定、udev 規則を別々の手作業にしないよう、既存の DKMS とパッケージ生成へ組み込みます。  
ただし、最初の実装では ABI と状態遷移の検証を優先し、配布処理の変更をプロトコル修正と同じコミットへ混ぜないでください。  

udev 規則は、pcscd がカードデバイスを開ける最小限の権限を設定します。  
誰でも書き込み可能なパーミッションで動作確認を済ませると、そのまま配布物へ残りやすいため避けてください。  

## 実装の進め方

### 既存 Linux 修正の基準測定

カード実装を始める前に、現在の `develop` をそのままビルドして受信結果を記録します。  
この測定が、カード実装後に発生した変化を判定する基準になります。  

```bash
make -C driver
```

次の情報を保存してください。  

- Linux ディストリビューションとカーネル版
- 使用したカーネルヘッダー
- 接続した機種、USB の接続先、アンテナ接続
- `/dev/px4video*` と物理チューナーの対応
- モジュール読込時と解除時のカーネルログ
- 各受信機の D、E、S、空受信時間
- チャンネル切り替え時の D、E、S

Linux 向けの既存修正は、Windows 環境ではカーネルヘッダーを用意できず、まだビルドしていません。  
このため、ビルド成功を前提にカード実装へ進まないでください。  

### プロトコル試験の移植

次に、ハードウェア I/O を模擬できるユーザー空間の T=1 実装と単体試験を作ります。  
カーネル側の完成を待たず、Windows 側の試験を同じ入出力で再現してください。  

移植元は [`winusb/tests/smart_card_state_test.cpp`](../winusb/tests/smart_card_state_test.cpp) です。  
最低限、次の症例をすべて含めます。  

- カード未挿入でもリーダーを open できること
- 挿入後に ATR と T=1 を初期化できること
- UART の受信可能待機
- 抜去後に状態を破棄し、再挿入後に再初期化すること
- カード検出と転送の失敗後に状態を回復すること
- WTX が無限に届いても APDU 全体が絶対期限 (3000ms) を大きく超えずに終了すること (移植元の試験は5秒未満で判定)
- 形式不正 ATR でリセットを1回だけ再実行し、前回の通信条件を残さないこと
- CRC、TA3、TC3、BWI を反映すること
- ACAS の TA1 `0x13`、38400bps、最初の IFS 消失後の RESYNCH と IFS 再送
- ACAS の IFSD 254
- LRC 使用時の254バイト APDUを251バイトと3バイトへ分割すること
- 対応外の TA1 を拒否すること

時間切れ試験は、単に失敗コードだけを確認せず、操作全体が再試行ごとに3000msずつ延びないことを実時間でも確認します。  
意図的に壊した ATR、LRC、CRC、連番、応答長で試験が失敗することも確認してください。  

### カーネルのカードデバイス

プロトコル試験と公開 ABI の要求が固まった後に、機種共通のカードデバイス層を追加します。  
最初は PX4 系の1機種で動かし、PX-Q3U4 の複数インターフェースと共有電源まで確認します。  

機種固有コードには、カード検出、電源取得と解放、`it930x_bcas_*()` への接続だけを置きます。  
ファイル操作、待機通知、USB 切断後の寿命管理は共通層へ集めます。  

PX4 系で確認した後に、PXMLT 系と ISDB2056 系へ接続します。  
各機種へ同じファイル操作を複製した場合は、抜去時の修正が機種ごとにずれるため、共通化の不足と判断してください。  

### PC/SC 接続

カーネルのカードデバイスを直接試験できた後に IFD ハンドラーへ接続します。  
pcscd のログで、カードスロットの数、挿抜、ATR、通信エラーを確認します。  

リーダー名には、複数台接続時に物理機器を識別できる安定した情報を含めます。  
USB の列挙順だけを識別子にすると、再接続後に別の機器へ同じ論理名が割り当てられる可能性があります。  
既存の Linux デバイス番号とシリアル番号の扱いを確認し、映像デバイスとの対応を追跡できる名前にしてください。  

### 実機試験

B-CAS で基本 APDU、抜去、再挿入を確認した後に、ACAS の B-CAS 互換機能を確認します。  
ACAS 試験では ATR、選択された38400bps、IFS、RESYNCH の発生有無を記録してください。  

カード単体の成功後は、TS を受信しながら APDU を繰り返します。  
少なくとも次の条件を分けて試験してください。  

- チューナーだけを使用
- カードだけを使用
- チューナーとカードを同時使用
- チューナーを先に閉じ、カードを継続使用
- カードを先に閉じ、チューナーを継続使用
- 最後の利用者を閉じた後の基板電源
- カード通信中のカード抜去
- カード通信中の USB 切断
- USB 再接続後の再列挙と再初期化

同時使用試験では、カードの APDU 失敗数と最大処理時間に加え、TS の同期エラー、transport error、continuity error、空受信を記録します。  
pcscd がリーダーを列挙できたことや、復号映像が短時間表示されたことだけで完了と判断しないでください。

[比較ページ](https://github.com/tsukumijima/px4_drv/compare/develop...makeding:px4_drv:linux-with-card-reader) は、PX-Q3U4 と ACAS の実通信を確認した資料として重要です。

## Windows 側の実測

Windows 検証環境では、PX-MLT5PE、DTV02A-1T1S-U (ISDB2056)、PX-W3U4 を接続し、それぞれの内蔵カードリーダーを列挙できることを確認しました。  
最新の x64 `winscard_api_test` は3台すべて成功し、外付けカードリーダーがない条件は `external_reader_tests=skipped (no system smart card reader)` と明示してスキップしています。  

3台で、TS 受信とカード APDU を同時に5分間実行し、TS とカードの失敗は0件でした。  
保存した TS の復号を含む `live_b25_reliability` も各機種で成功しています。  

PX-W3U4 の BS と CS は、Windows 検証環境に衛星波のアンテナを接続していないため試験していません。  
Linux 側や他環境で受信実績があるため、この条件の確認を Linux カード実装の開始前提にする必要はありません。  

PX-W3U4 の地上波では、通常の自動選択で T0 が T1 より先に選ばれることを確認しました。  
T1 を先に明示指定してから T0 を使用すると、既知の T1 から T0 へのドロップを意図的に再現できました。  
[PR #2](https://github.com/tsukumijima/px4_drv/pull/2) の通常選択順は現在も機能しており、この試験は回避策を無効にした条件です。  

Linux のデバイス番号は、現状では同一グループ内で T0 が `/dev/px4video2`、T1 が `/dev/px4video3` になる構成です。  
Mirakurun のチューナー定義も T0 を先に並べると、通常利用で T1 から T0 の順に開く機会を減らせます。  
T1 使用中に T0 しか空いていない場合まで禁止するものではないため、ハードウェア干渉を完全に解消する変更ではありません。  

受信試験の際、放送休止時間帯のチャンネルを受信できないことを選局失敗と混同しかけた事例がありました。  
Linux 側の受信確認でも、放送休止をドライバの選局失敗として記録しないよう、試験時刻と番組表を確認してください。  

## 完了判定

### ビルド

- 対象カーネルのヘッダーを使い、`make -C driver` が成功すること
- カーネルモジュールの読込と解除で警告、参照漏れ、use-after-free が発生しないこと
- IFD ハンドラーとプロトコル単体試験が、対象の配布環境でビルドできること
- DKMS とパッケージ生成から必要なカーネルモジュール、IFD ハンドラー、udev 規則を配置できること

### プロトコル

- Windows 側の `smart_card_state_test` に相当する全症例が Linux 側でも成功すること
- 壊した ATR、LRC、CRC、連番、応答長を陽性対照として、試験が意図どおり失敗すること
- WTX を含む異常応答でも、APDU 全体の絶対期限を超えて待ち続けないこと
- 254バイト APDU を UART 上限に合わせて分割できること
- B-CAS と ACAS の初期化順序を区別できること

### 機器寿命と電源

- カード open 中にチューナーを閉じても基板電源が維持されること
- チューナー使用中にカードを閉じても基板電源が維持されること
- 最後の利用者が閉じると基板電源が停止すること
- Q3 系の同一筐体へカードデバイスを重複登録しないこと
- PXMLT8PE3 側へカードデバイスを登録しないこと
- USB 切断で待機中の処理が終了し、以後の機器操作が `-ENODEV` になること
- USB 切断後も open 中のファイル記述子による参照が安全に残り、close 後に解放されること

### PC/SC と実機

- pcscd が物理カードスロットと同じ数の内蔵リーダーを列挙すること
- 外付けカードリーダーを接続した場合も、既存の列挙と共有動作を維持すること
- カード未挿入のリーダーを列挙し、挿入後に利用できること
- カード抜去、再挿入、USB 抜去、再接続後に pcscd を含む状態が回復すること
- B-CAS で基本 APDU を繰り返し実行できること
- ACAS の B-CAS 互換機能で基本 APDU を実行できること
- TS と APDU の同時負荷で、カード失敗、同期エラー、transport error、continuity error、空受信が基準測定から悪化しないこと

## 実装時に避けること

- makeding 氏、onpat 氏、yyya-nico 氏のブランチ全体を、そのまま取り込むこと
- `it930x_bcas_*()` と同じレジスタ操作を機種側へ複製すること
- T=1 の状態機械と長い応答待ちをカーネルへ置くこと
- 再試行のたびに操作全体の期限を延長すること
- カード抜去後に ATR、連番、CRC、IFSC、BWI を残すこと
- カードとチューナーの電源状態を、相互に無関係な真偽値だけで管理すること
- 同じ物理スロットへ複数のカードデバイスを登録すること
- USB 切断時に open 中の参照を無視して機器オブジェクトを解放すること
- カーネルや製品コードへ B-CAS ATR の許可一覧を埋め込むこと
- pcscd の列挙成功だけで、受信への影響まで確認済みと判断すること
- 外付けカードリーダーがない試験環境を、内蔵リーダー試験全体の失敗にすること

## 実装開始時の確認項目

Linux 側の最初の作業では、次の順で事実を固定してください。  

1. HEAD と上記コミット群の存在を確認
2. 現在の `develop` を対象カーネルでビルド
3. カード実装前の TS 受信結果とカーネルログを保存
