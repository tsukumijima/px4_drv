## カード状態遷移の自動試験

### 実行対象

[`smart_card_state_test.cpp`](../winusb/tests/smart_card_state_test.cpp) は、模擬 `CardDevice` を使って ATR、T=1、抜去、エラー、時間制限を試験します。  
`build.ps1` は x86 と x64 の両方でこの試験を実行する構成です。  

この開発作業では、追加した ACAS と APDU 分割の症例を含め、カード状態遷移試験の成功を確認しました。  
テスト実行時の全コンソール出力はリポジトリへ保存していません。  

### 確認した正常系

- カード未挿入でも UART を開いたリーダーとして待機できること
- カード挿入後に ATR を取得し、T=1 を初期化できること
- 受信可能通知を待ってから UART の完成フレームを読むこと
- TA3 の IFSC、TB3 の BWI、TC3 の LRC または CRC を反映すること
- B-CAS で RESYNCH の後に IFS を送ること
- ACAS で IFS から開始すること
- ACAS の TA1 `0x13` で38400bpsへ切り替えること
- ACAS で IFSD 254を要求すること
- 254バイト APDU を LRC 使用時に251バイトと3バイトへ分割すること
- カードからのチェーン I-block を連結して返すこと

### 確認した異常系

- カード抜去で ATR、IFSC、EDC、BWI、送受信連番を破棄すること
- 再挿入後に以前のセッションを使わず再初期化すること
- カード検出エラーと転送エラーの後に状態を無効化すること
- 形式不正 ATR だけカードリセットを1回再実行すること
- ATR の再試行間で前回の通信条件を残さないこと
- 対応外の TA1 を拒否すること
- 最初の ACAS IFS が失われた場合に RESYNCH と IFS で回復すること
- WTX が続いても APDU 全体の絶対期限で終了すること
- 応答バッファが不足した場合に成功扱いしないこと
- LRC、CRC、連番、ブロック形式が不正な場合にプロトコルエラーを返すこと

### 自動試験が測っていないこと

模擬カードは、実機の USB 制御転送遅延、UART FIFO の不安定な時刻、カード接触不良を再現できません。  
TS とカード通信が同じ IT930x を使う際の競合も、この試験では測れません。  

ACAS の ATR と応答を模擬しているため、実際の ACAS カードが Windows 検証環境で通信したことの証明にもなりません。  
これらの不足は実機試験と外部実測で別に扱います。  

## WinSCard API の自動試験と実機試験

### 最新の x64 実行

外付けカードリーダーを外した状態で、x64 の [`winscard_api_test.cpp`](../winusb/tests/winscard_api_test.cpp) を実行しました。  
PX-MLT5PE、DTV02A-1T1S-U (ISDB2056)、PX-W3U4 の内蔵リーダー3台を列挙し、カードが挿入された PX4 リーダーの API 試験はすべて成功しました。  

最終行は `readers=3 result=passed` でした。  
外付けリーダー固有の試験は `external_reader_tests=skipped (no system smart card reader)` と明示して省略しました。  

### API 試験で確認した契約

- 内蔵リーダーが System32 側のリーダーより先に列挙されること
- 内蔵リーダー名とデバイスインスタンス ID の16桁識別子が対応すること
- ANSI と Unicode のリーダー一覧が一致すること
- `SCARD_AUTOALLOCATE` と `SCardFreeMemory()` の所有権を処理できること
- 共有接続と排他接続の競合を拒否できること
- トランザクションと再接続を処理できること
- ATR、状態、プロトコルを取得できること
- PX4 内蔵リーダーへ B-CAS の基本 APDU を送受信できること
- 未知のリーダー名と長すぎるリーダー名を成功扱いしないこと
- 外付けリーダーがない場合も、内蔵リーダーの試験を継続すること

### 外付けリーダーの扱い

最新実行時は外付けカードリーダーを物理的に接続していません。  
このため、System32 側の物理リーダー接続、`SCardAccessStartedEvent()`、外付けカードへの APDU、外付けリーダー上の ANSI API は最新実行で確認していません。  

初期実装時には、SCR33xx 系の外付けリーダーについて、内蔵リーダーとの同時列挙と外付け単独のリアルタイム復号を確認しています。  
この過去の実測は外付け経路の基本設計を支えますが、2026年7月24日の最終コミット列を適用した最新回帰試験ではありません。  

外付けリーダーがない場合に Windows の Smart Card サービスが停止していることは、PX4 内蔵リーダー経路の失敗を意味しません。  
内蔵リーダーは WinSCard_PX4 から DriverHost_PX4 のカードサーバーへ接続するため、System32 側の物理リーダー試験と分けています。  

x86 の `winscard_api_test.exe` はビルド済みですが、最終変更後に3台の実機で再実行した記録はありません。  
最新の実機 API 結果は x64 に限定します。  

## Windows の接続機器

### PX-MLT5PE

Windows 検証環境へ接続し、内蔵リーダーの列挙、カード APDU、TS 受信とカード通信の同時負荷、保存 TS の復号を確認しました。  
PX-MLT5PE は PXMLT 系の共有電源とカードスロット判定を確認する実機です。  

Windows 検証環境で使用したカードの ATR を最終ログへ保存していないため、カードが B-CAS か ACAS かをこの記録から確定できません。  
カード通信成功は確認済みですが、カード種別は未確認として残します。  

### DTV02A-1T1S-U (ISDB2056)

Windows 検証環境へ接続し、内蔵リーダーの列挙、カード APDU、TS 受信とカード通信の同時負荷、保存 TS の復号を確認しました。  
ISDB2056 は通常の `0x47` 同期バイトを使い、同じ IT930x 上で TS と UART の制御転送が進むため、同時負荷を重視しました。  

初期実装時に調べた断続的スクランブルとチャンネル切り替えの詳細は [`20260724_winusb_card_reader_debugging_history.md`](20260724_winusb_card_reader_debugging_history.md) を参照してください。  
最終的な短時間試験では、カード追加による受信失敗を確認していません。  

### PX-W3U4

Windows 検証環境へ接続し、地上波側で内蔵リーダーの列挙、カード APDU、TS 受信とカード通信の同時負荷、保存 TS の復号を確認しました。  
通常設定では T0 が T1 より先に選ばれることも確認しました。  

PX-W3U4 の BS と CS はアンテナ線を接続していないため、Windows 検証環境では試験していません。  
BS と CS の未試験は物理配線による制約であり、失敗結果ではありません。  

## TS とカードの同時負荷

### 実行した試験

[`card_stream_stress.cpp`](../winusb/tests/card_stream_stress.cpp) に相当する同時負荷を、PX-MLT5PE、DTV02A-1T1S-U (ISDB2056)、PX-W3U4 の3機種でそれぞれ5分間実行しました。  
TS を受信しながら、同じ内蔵カードリーダーへ2接続から基本 APDU を繰り返す条件です。  

3機種とも、記録した試験範囲ではカード APDU 失敗、TS 同期エラー、transport error、continuity error は0件でした。  
この結果から、通常受信中のカード通信に直ちに現れるデグレードは確認されていません。  

### 試験時間の限界

5分間の成功は、数時間から数日の録画を保証しません。  
USB 再接続、温度変化、カード接触、アプリケーションの異常終了が重なる条件も含みません。  

この試験は、カード機能を追加した直後から TS が欠落する種類の問題を検出するものです。  
Issue #38 のような稀な長期状態は、別の検証として残します。  

## 保存 TS の復号

[`live_b25_reliability.cpp`](../winusb/tests/live_b25_reliability.cpp) を使い、PX-MLT5PE、DTV02A-1T1S-U (ISDB2056)、PX-W3U4 の各受信経路で、内蔵カードを使った復号が成功することを確認しました。  
入力と出力の同期エラー、復号失敗、出力スクランブルが成功条件に含まれます。  

各実行の最終コンソールログと正確な継続時間はリポジトリへ保存していません。  
このため、成功の有無は記録できますが、最大復号時間などの数値比較には使えません。  

## PX-W3U4 の T0 と T1

### 通常順序

通常の自動選択では、T0 が T1 より先に選ばれました。  
[PR #2](https://github.com/tsukumijima/px4_drv/pull/2) が意図した危険な順序の回避は、Windows 検証環境の通常設定で機能しています。  

この結果は、すべてのヒープ配置と全接続順で必ず T0 が先になることの証明にはなりません。  
追加の明示ソートは、再現性と既存選択への影響を比較して見送りました。  

### 意図的な T1 先行

T1 を明示指定して開いた後に T0 を開くと、T1 側のドロップを再現しました。  
この試験は、PR #2 の通常選択を使わず、既知の干渉条件を意図的に作ったものです。  

この結果は、PR #2 が効いていない証拠にはなりません。  
ハードウェア内部の干渉が残ることと、通常順序で問題条件を避けることを別の事実として扱います。  

### 放送休止と選局失敗の区別

深夜にチャンネル13で TS が届かなかった試行は、Eテレの放送休止時間と一致しました。  
この試行は、T1 と T0 の順序、ReceiverManager、選局失敗の不具合へ数えていません。  

将来のチャンネル切り替え試験では、試験時刻と放送状況を同じログへ残してください。

## ACAS の検証範囲

### 確認済み

- TA1 `0x13` から38400bpsを選ぶコード
- IT930x UART mode 1 の38400bpsリロード値 `0xef`
