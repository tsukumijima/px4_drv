# 2026年10月18日 ISDB-C 対応の取り込みと実機確認の記録

この文書は、PX-MLT 系のケーブルテレビ (ISDB-C) の受信に対応したフォークを取り込んだ経緯と、実機での検証結果、未検証の範囲をまとめたものです。  
使い方は [README](../README.md) の「ケーブルテレビとスカパー！プレミアムサービス光の受信」に、選局の仕様は [ISDB-C と J.83 Annex B の選局の仕様](isdbc_tuning.md) にあります。

## 検証環境

- Windows 11 (x64) に PX-MLT5PE を PCIe で接続し、WinUSB 版の DriverHost_PX4 と BonDriver を使用
- アンテナ端子には、イッツコムの CATV 回線をつないだ (地デジのパススルー・BS の IF・ISDB-C が同じ同軸ケーブルで届く)
- Linux 版は、同じ PX-MLT5PE を usbipd-win の USB/IP で WSL2 (Ubuntu 24.04) へ渡して確認した。USB/IP を経由するため、TS の誤りの数はネイティブ Linux の結果として評価していない
- 受信の確認には、BonDriver を直接読み込んで選局と TS の保存を順に行う試験用のツールと、同期・TEI・PID ごとの CC・PAT の TSID・SDT のサービスを数えるスクリプトを使った

## 取り込んだもの

PX-MLT 系の ISDB-C 対応は、次のフォークで進められていました。

| フォーク | 内容 |
|---|---|
| [n0atl/px4_drv](https://github.com/n0atl/px4_drv) の `isdbc-edition` | Linux 版と WinUSB 版の ISDB-C (64QAM) の最初の実装 |
| n0atl/px4_drv の `feature/tsmf-tlv-v61` | WinUSB 版の 256QAM・TSMF の分離・生 TLV 出力 |
| [aoiro-labo/px4_drv](https://github.com/aoiro-labo/px4_drv) の `feature/tsmf-tlv-v61` | 上の版に、J.83 Annex B (5.6Msps) の受信と、ケーブル受信後のチューナー停止の修正を追加 |
| [nanamitm/px4_drv](https://github.com/nanamitm/px4_drv) の `develop` | macOS 版と上の版を統合し、公開ドライバー由来の参照プロファイルを追加 |

aoiro-labo 氏のブランチが、n0atl 氏の ISDB-C・TSMF・TLV のコミットと J.83B をすべて含んでいたため、これをマージで取り込みました。  
macOS 版は、このリポジトリの対象から外れるため取り込んでいません。

## 取り込んだ後の作り直し

取り込み元は、調査のための経路を残したまま機能を積み上げた作りでした。  
ISDB-C は INI とモジュールパラメーターで有効にする実験的な機能で、有効にすると地デジと BS/CS の受信でも null パケットの除去がブリッジから DriverHost へ移り、選局のループと TS の書き込みも全機種で新しいコードを通っていました。

そこで、develop からの差分を ISDB-C に必要な行だけに絞り、ISDB-C を既定で使える形に作り直しました。

- 選局のループ、TS の書き込み、IT930x の null パケットの除去、復調器とチューナーの ISDB-T / ISDB-S の関数は develop と同じコードを通り、ISDB-C のときだけ別の関数へ分岐する
- TSMF の TS を選ぶ処理は TSMF の TS を指定したときだけ動き、IT930x の null パケットのフィルターもそのときだけ切る (TSMF はヘッダーの直後の52パケットの位置で TS を選ぶため、ブリッジで null パケットを除くと位置がずれる)
- TSMF の分離は Linux 版と WinUSB 版で共有する `driver/tsmf.c` にまとめ、両方で同じ処理を使う
- TSMF で選んだパケットは、次のヘッダーがちょうど52パケット後に届いて1フレームがそろったと分かってから出力する。受信の欠落でスロットの位置がずれたフレームは出力しないため、別の TS のパケット (PAT など) を録画へ出力しない
- ISDB-C の停止では、Sony の手順 (`AICtoSL()`) と同じく、ISDB-C の起動で書き換えた復調器の設定を既定値へ戻す。戻せなかったときは、ISDB-C の設定が残ったまま受信しないよう、地デジと BS/CS の起動を中断する
- J.83 Annex B は、機種の ISDB-C 全体を置き換える INI の設定をやめ、ChSet の行ごとに選べるようにした
- 比較用の参照プロファイル、変調方式の上書き、J.83B のモニター、ログファイルへの出力、診断用の計数、根拠のない TSMF の slot offset 、ソリューションにもビルド手順にも組み込まれていなかった試験を外した

## 実機で分かったこと

### 変調方式の指定は不要

取り込み元は、変調方式の指定がなければ 64QAM を試し、TS が届かなければ 256QAM を試していました。  
実際に試すと、64QAM の搬送波 (C51・C52) を 256QAM の指定で選局しても、誤りなしで受信できました。  
一方、256QAM の搬送波 (UHF 20ch) を 64QAM の指定で選局すると、ロックしても TS が届きませんでした。

復調器は QAM の次数を自動で判別していて、この指定が実際に変えていたのは TS の出力の設定 (0xd1 と 0x33 を0にする設定) だけでした。  
ISDB-C では常にこの出力の設定を使うようにし、変調方式の指定と 64QAM → 256QAM の再試行を外しました。  
この出力の設定は、後に公式ドライバーが PX-MLT 系に使う設定へ置き換えています (「公式ドライバーとの照合」を参照)。  
256QAM の搬送波の選局は、0.65 秒から 0.19 秒になりました。

### CXD2841ER 用のアナログ設定は不要

取り込み元は、256QAM のときだけ Linux の `cxd2841er.c` の DVB-C 用のアナログ設定 (0x59・0x2f・0x30・0x41・0x43〜0x44) を CXD2856ER に書いていました。  
これらは CXD2841ER の ADC の設定で、CXD2856ER の地デジの起動処理は書き直さないため、256QAM の後に地デジを選局すると値が残ります。  
外しても 256QAM を誤りなしで受信できたため、削除しました。

### 周波数の補正は不要

取り込み元の ChSet には、周波数に比例して -200kHz から -925kHz まで増える補正が入っていました。  
チューナーに 24MHz の水晶用の値 (REF_R) を書いていたことによるずれと見られ、16MHz 用の値に直した後は、補正がない方が C/N が良くなりました。

| 搬送波 | 補正 0 | -250kHz | -525kHz | +250kHz |
|---|---|---|---|---|
| C51 (64QAM) | 26.10dB | 26.01dB | 25.69dB | 25.79dB |
| UHF 20ch (256QAM) | 32.94dB | 32.79dB | - | 32.64dB |

UHF 20ch は、取り込み元の補正 (-650kHz) のままでは選局できませんでした。  
局ごとのずれを手で合わせる必要も見つからなかったため、ChSet から補正の列を削除しました。

## 確認できたこと

### 受信

同じ受信機で、ISDB-C・地デジ・BS を10秒ずつ交互に選局しました。

| 選局 | 結果 |
|---|---|
| C51 (64QAM) | 誤り0件、C/N 26.1dB |
| UHF 20ch (256QAM) | 誤り0件、C/N 32.9dB |
| C52 の相対 TS 0 と TSID 17488 | 誤り0件、TSID 17488 の TS だけを出力 |
| C52 の TSID 16895 (毎秒 4〜140KB の低レートの TS) | 誤り0件 |
| C52 の存在しない相対 TS 1 と TSID 9999 | 選局に失敗 |
| VHF 4ch (物理チャンネル番号 13) | 受信でき、C/N 23.1dB で transport error と CC の不連続が4件 |
| 地デジ 27ch と BS15 (ISDB-C の選局の前後) | 10秒あたりの受信量と C/N が ISDB-C の選局の前後で同じ |

地デジ 27ch では、0x140・0x160・0x170 などの低レートの PID だけに CC の不連続が数秒おきに出ます。  
develop の版でも同じ PID に同じ形で出て、映像の PID には出ないため、放送側の多重によるものです。

64QAM の C52 (相対 TS 0) を3分間、C51 を2分半、別々の受信機で同時に受信し、どちらも同期・TEI・CC の誤りは0件でした。

### 低レートの TS で最初のデータが届くまでの時間

TSID 16895 は、データ放送の PID が流れている間は毎秒約 140KB 、止まっている間は PAT と PMT だけの毎秒約 4KB になる TS です。  
BonDriver は 1024 パケット (約 188KB) のバッファーが埋まってから渡し、選局の直後の1つは捨てるため、そのままでは最初のデータまで数秒から数十秒かかっていました。  
そこで、TSMF の TS を選んでいる間は DriverHost が出力のたびに読み出し側へ知らせ、ISDB-C の選局中は BonDriver が 200ms で途中まででもバッファーを渡すようにしました。  
地デジや BS/CS は 188KB を 0.1 秒前後で埋めるので、従来どおり埋まってから渡します。

地デジ 27ch の直後に TSID 16895 を12回選局すると、最初のデータまでの時間は 0.25〜0.37 秒で、その後のデータの間隔も最大 0.3 秒でした。

### Linux 版

同じ PX-MLT5PE を WSL2 へ渡し、同じデバイスファイルで地デジ・ISDB-C・BS を10秒ずつ順に受信しました。

| 選局 | 結果 |
|---|---|
| 既存の ioctl (`PTX_SET_SYSTEM_MODE` + `PTX_SET_CHANNEL`) の C51 と UHF 20ch | 誤り0件 |
| 拡張 ioctl (`PTXT_SET_PARAMS` + `PTXT_TUNE`) の C51 と UHF 20ch | 誤り0件 |
| 拡張 ioctl の C52 の相対 TS 0・TSID 17488・TSID 16895 | 誤り0件、指定した TS だけを出力 |
| 拡張 ioctl の C52 の存在しない相対 TS 1 | `EAGAIN` で選局に失敗 |
| 受信中の `PTX_GET_CNR` (C52 の TSID 17488 と UHF 20ch) | 28.1〜28.3dB と 33.1〜33.6dB (UHF 20ch は Windows 版の 32.9dB と同程度) |
| 地デジ 27ch と BS15 (ISDB-C の選局の前後) | 受信でき、地デジの CC の不連続は Windows と同じ放送側によるものだけ |

## 未検証の範囲

- PX-MLT5PE 以外の機種 (PX-MLT8PE・DTV02A-5TS-P・DTV02A-4TS-P・PX-MLT5U) と、イッツコム以外のケーブルテレビ局
- 長時間の録画と、5つの受信機での同時受信 (取り込み元の作者は、生 TLV を含む5受信機の同時受信で約3分ごとに全受信機が同時に欠落したと報告していて、原因は分かっていない)
- J.83 Annex B (この環境には J.83 Annex B の信号がないため、I2C の通信を模擬した試験だけで検証した)
- 生 TLV の出力 (この環境で 4K の TLV が載った搬送波を探していない)
- ネイティブ Linux での受信
## 公式ドライバーとの照合

2026年10月25日に、復調器 (CXD2856ER) とチューナー (CXD2858ER) の ISDB-C と J.83B の設定を、PLEX が公開している Linux ドライバーの Sony のコードと1つずつ照合しました。  
照合には、PLEX の Linux ドライバーを収めた [soralis0912/it930x_driver_native](https://github.com/soralis0912/it930x_driver_native/tree/64fd4f3fd04cd8c19855250ebd88278734d4eba6) の次のファイルを使いました。

| ファイル | 内容 |
|---|---|
| `api/DW_Frontend/CXD2856/isdb_cable/sony_demod_isdbc.c` | ISDB-C の起動 (`SLtoAIC()`)・選局し直し (`AICtoAIC()`)・停止 (`AICtoSL()`)・TSMF の設定 |
| `api/DW_Frontend/CXD2856/isdb_cable/sony_demod_isdbc_monitor.c` | ロックの判定と C/N の式 |
| `api/DW_Frontend/CXD2856/sony_demod.c` | TS クロックの設定と、IF の既定値 (ISDB-C は 3.7MHz、J.83B 5.6Msps は 3.75MHz) |
| `api/DW_Frontend/CXD2856/tuner/terr_cable_sat_helene/refcode/sony_helene.c` | チューナーの方式ごとの設定表と選局手順 |
| `api/DW_Frontend/CXD2856/CXD2856.c` | PX-MLT 系の初期化 (復調器の I2C アドレスと TS クロック) |

取り込み元は、DVB-C 用の Linux の `cxd2841er.c`・`helene.c` を下敷きに ISDB-C を組み立てていました。  
そのため、次の違いはすべて ISDB-C 対応の取り込みで入ったもので、develop の地デジと BS/CS の処理には含まれていません。  
停止の処理だけは、取り込んだ後の作り直しで加えた保存と書き戻しの仕組みでした。

| 違い | 公式の値 | 取り込み後の値 | 影響 |
|---|---|---|---|
| 復調器の動作モード (SLV-X 0x17) | 0x09 (ISDB-C) | 0x04 (DVB-C) | DVB-C として復調していた |
| フィルター係数 (バンク 0x10 の 0xa6〜0xb3) | Sony のチューナー用の ISDB-C の係数 | DVB-C 6MHz の係数 | 帯域の形が公式と異なっていた |
| IF (バンク 0x10 の 0xb6〜0xb8) | 0x13bbbc | 0x13bbbb | 最下位の1だけの差 |
| IF AGC の待ち時間 (バンク 0x11 の 0x33〜0x35)・同期ロックの使用 (バンク 0x48 の 0x2c) | 書く | 書かない | 地デジの起動の後でなければ既定値のままだった |
| QAM の探索範囲・シンボルレートの探索値 (バンク 0x40 の 0x14・0x1e・0x26〜0x29) | ISDB-C 用の値 | DVB-C 用の値の一部 | 探索の条件が公式と異なっていた |
| バンク 0x10 の 0xd2 | 書かない | 書く | 公式にない書き込み |
| ISDB-C の TS クロック | ゲート式・ハーフレート・高い周波数 | DVB-C 用の設定 | PX-MLT 系の基板で公式が使う設定と異なっていた |
| J.83B の TS クロック | ISDB-C と同じ設定で、パケット間の隙間の挿入だけを有効にする | 連続クロック・フルレート・中間の周波数 | 同上 |
| ISDB-C の停止 | 既定値へ戻す4つの設定を書いてから停止する | 起動前の値を保存して書き戻し、地デジと同じ手順で停止する | 公式と異なる手順で停止していた |
| ISDB-C のまま選局し直すとき | TS の出力を止めるだけ | 起動の処理をすべてやり直す | 公式より多くの書き込みをしていた |
| チューナーの IF_BPF_GC (0x69 の下位4ビット) | 0x04 (CXD2856 世代の表) | 0x05 (旧世代の表) | J.83B はもとから 0x04 で一致 |

これらはすべて公式の値へ直しました。  
TSMF は、公式は復調器で TS を選びますが、このリポジトリは Linux 版と WinUSB 版で共有する `driver/tsmf.c` で選ぶ作りを維持し、復調器の TSMF 処理は単一の TS として扱う設定 (OREG_TSMF_MODE = 0) にしています。  
この設定でも、TSMF のヘッダーを含む多重化された TS が復調器からそのまま届き、C52 の TS を相対 TS 番号と TSID のどちらでも選べることを実機で検証しました。

一方、次の項目は公式と一致していました。

- チューナーの ISDB-C と J.83B の設定 (REF_R、FIF_OFFSET、BW_OFFSET、0x5e〜0x66 と 0x75〜0x78 の値、選局後の50ミリ秒の待ち)。公式は、ISDB-C と J.83B の 5.06・5.36Msps で DVB-C 6MHz の設定を使い、日本の J.83B の 5.6Msps だけ FIF_OFFSET と BW_OFFSET が異なる専用の設定を使う
- ロックの判定 (バンク 0x40 の 0x88 のビット0と、0x10 のビット5)
- C/N の式 (`-9500 × ln(IREG_SNR_ESTIMATE) + 95941`、dB の1000倍、生値の下限は126)
- 受信機ごとの復調器の I2C アドレス (PX-MLT5PE は受信機 0〜4 の順に 0xCA・0xD8・0xC8・0xD8・0xC8)

C/N は、公式は AR ロックと QAM の次数 (64QAM か 256QAM) を調べてから計算し、それ以外ではエラーを返します。  
このリポジトリはロックの確認をせずに値を返していて、この違いは地デジと BS/CS の C/N の読み出しと同じ扱いのため、今回は変えていません。

PLEX の Linux ドライバーには J.83B の復調器の手順 (`sony_demod_j83b.c`) が含まれていません。  
J.83B の復調器の起動と停止は、Sony の手順を移した TBS の `cxd2878.c` ([koreapyj/cxd28xx](https://github.com/koreapyj/cxd28xx/blob/c5fa27eecbe80633cbb365cc44656daea1c0e2e3/cxd2878.c)、GPL-2.0-only) の値を使い、TS クロックだけを PLEX の PX-MLT 系の設定にそろえました。  
停止の最後の処理も、`cxd2878.c` と同じく地デジ固有の設定を書かない共通の手順に直しました。

### 地デジの TS クロック

PLEX の `CXD2856.c` は、地上波・ケーブルの TS クロックを 38.4Mbps の設定にした直後に 64Mbps の設定で上書きしていて、地デジも 64Mbps で出力します。  
develop の地デジは 38.4Mbps 相当の設定で、地デジの TS は収まるため、今回の変更の対象外です。  
256QAM の ISDB-C (約 38.9Mbps) と J.83B は 38.4Mbps に収まらないため、公式どおり 64Mbps 相当の設定を使います。

### PX-MLT5PE の受信機 0・1 で J.83B を受信できない報告

PX-MLT5PE (V1.0) で、受信機 0 と 1 だけ J.83B の TS が届かず、2〜4 と地デジ・BS/CS は受信できるという報告がありました。  
同じ報告で、V2.0 の PX-MLT5PE と PX-MLT8PE では5つとも受信できています。  
復調器の I2C アドレスと受信機の対応は公式と一致していたため、照合で見つかった違いのうち受信機ごとに結果が変わりうるものは、J.83B の TS クロック (連続クロック・フルレート) です。  
この TS クロックを公式の設定に直しましたが、この環境には J.83B の信号がなく、報告と同じ条件では検証していません。  
直した後の ISDB-C (64QAM と 256QAM) は、受信機 0〜4 のすべてで誤りなく受信できました。

### 照合の後の実機確認

PX-MLT5PE の受信機 0〜4 をそれぞれ固定し、WinUSB 版で地デジ 27ch・BS15 (TS0)・C51・UHF 20ch・C52 の TSMF (相対 TS 0 と TSID 17488)・地デジ 27ch を10秒ずつ順に選局しました。  
5つの受信機の35回の選局すべてで、同期・TEI・CC の誤りは0件でした。

C/N は、照合の前のコミットと交互に2回ずつ測った値がほぼ同じでした (C51 は 29.9〜31.0dB、UHF 20ch は 35.0〜35.5dB)。  
照合による修正で受信の余裕が変わったとは言えません。

Linux 版は、同じ PX-MLT5PE を WSL2 へ渡し、受信機 0 と 1 で地デジ・BS・C51・UHF 20ch・C52 の TSMF を順に受信しました。  
ISDB-C はすべて誤り0件で、`PTX_GET_CNR` は C51 で 30.0〜31.2dB 、UHF 20ch で 35.0〜35.9dB でした。  
存在しない相対 TS 1 の指定は、照合の前と同じく `EAGAIN` で失敗しました。  
受信機 0 の最初の地デジだけ、受信開始の直後に低レートの PID (0x160・0x170・0x581) で CC の不連続が3件あり、上の「確認できたこと」の放送側の不連続と同じ PID です。

## 選局の指定方法の作り直し

2026年10月26日に、チャンネル定義と選局の指定方法を、配布するチャンネル定義を編集せずにどのケーブルテレビ局でも使える形に作り直しました。  
ISDB-C 対応はまだリリースしていないため、これまでの指定方法との互換は残していません。

### 変えたこと

- TSMF の TS は、ヘッダーで有効な TS を相対 TS 番号の順に並べたときの何本目か (1〜15) だけで選ぶ。相対 TS 番号・TSID・生 TLV の指定は、チャンネル定義・名前付きパイプ・Linux の ioctl から削除した
- ISDB-C の受信はすべて TSMF の分離処理を通し、ヘッダーのない搬送波は1本目の指定でそのまま出力する。TLV を運ぶ TS かどうかは、ヘッダーの stream_type から決める
- ヘッダーのない搬送波と判断した後でもヘッダーが届けば TSMF の搬送波として選び直し、一度ヘッダーを受け取った後はヘッダーが途切れても素通しにしない (選局の直後に受信が乱れても多重化された TS を録画し続けず、別の TS のパケットも出力しない)
- J.83 Annex B は TSMF を使わないため分離処理を通さず、地デジと同じくブリッジで null パケットを除く。TSMF の2本目以降の指定は受け付けない
- Linux の受信開始では、選局で決めた判断を保ったままフレームの途中の状態だけを捨てる (受信開始のたびに先頭のパケットを捨てない)
- 配布のチャンネル定義は、物理チャンネルごとに1本目から4本目までの行を置き、J.83 Annex B を別のチューニング空間にした。J.83 Annex B の行は中心周波数で書き、H01〜H77 に加えて、BonDriver_BDA が選べるようにしている H11〜H12 の +1MHz と H26〜H28 の +4MHz の周波数も並べた
- J.83 Annex B のまま選局し直すときは、Sony の `ACCtoACC()` と同じく TS の出力を止めて帯域の設定だけを書き直す
- ISDB-C と J.83 Annex B のロック待ちを、Sony の `sony_integ_isdbc_WaitTSLock()` と `sony_integ_j83b_WaitTSLock()` と同じ1秒にした
- Linux の `PTXT_TUNE` は、ロックしない場合を `EAGAIN` 、指定した何本目の TS がない場合を `ENODATA` で返す

### 実機で分かったこと

イッツコムの C51 は、TS が1本だけの搬送波ですが TSMF のヘッダーが付いています。  
ヘッダーの stream_type は、C51・C52・C14 などの MPEG-2 TS で 1 になっていて、取り込み元の「0 なら分割 TLV」という読み方と矛盾しませんでした。

C51 から UHF 20ch (ヘッダーのない 256QAM の搬送波) へ選局し直すと、選局は成功するのに TS が1バイトも届かないことが、10回中10回起きました。  
選局し直した直後は、IT930x の転送1回分に C51 の TS が残っていて、20ch のロックの後に届きます。  
ロックしてから TSMF の判定をやり直しても、この残りのヘッダーを読んで 20ch を TSMF の搬送波と判定し、次のヘッダーを待ち続けていました。  
選局の最後に復調器をソフトリセットするため、ロックの表示が前の搬送波のまま残ることはありません (ロックしている 20ch から信号のない C13 への選局は、1秒のロック待ちで失敗しました)。  
この不具合は、作り直しの前の版では TSMF を指定しない選局が分離処理を通らないため起きず、同じ並びを6回試してすべて受信できました。

前の搬送波の残りを測ると、新しい搬送波の判定をやり直してから最大 710 パケット目まで前の搬送波のヘッダーが届きました。  
既定の転送の単位 (816パケット) に収まるため、判定をやり直した直後の転送1回分のパケットを捨てるようにしたところ、C51 から 20ch への選局は20回すべてで受信でき、20ch の直後の C14 の2本目も10回すべてで選局できました。

信号のない搬送波は、ロック待ちの上限 (`TuneTimeout` の5秒) まで待ってから失敗していました。  
Sony のコードには ISDB-C と J.83 Annex B の信号がないことを示すビット (`IREG_AR_TIMEOUT`) がありますが、スキャン専用の設定 (`OREG_AR_SCANNING`) を有効にしたときだけ働きます。  
録画中に信号が途切れたときの捕まえ直しに影響しうるため、この設定は使わず、ロック待ちを Sony の通常の選局と同じ1秒にしました。  
信号のない搬送波の選局の失敗は、WinUSB 版で約 5.1 秒から約 1.1 秒になりました。

### 確認結果

WinUSB 版は、PX-MLT5PE の受信機 0 で、次のチャンネルを8秒ずつ順に選局しました。

| チャンネル | 結果 |
|---|---|
| 地デジ 27ch・BS15 (TS0) | 受信、誤り0件 |
| C51 (TSMF のヘッダー付き、TS 1本) | 受信 (TSID 16625)、誤り0件 |
| C51 の2本目 | 約 0.2 秒で選局に失敗 |
| UHF 20ch (256QAM、ヘッダーなし) | 受信 (TSID 63237)、誤り0件 |

それぞれ、守っている行を壊した版で試験が失敗することを検証しています。

### 未検証の範囲

- J.83 Annex B の実際の信号での受信 (H01〜H77 の周波数・選局し直しの手順を含む)
- 4K の TLV を運ぶ搬送波での TLV の出力
- 受信ソフトウェアでのチャンネルスキャン。BonDriver を直接読み込む試験用のツールで、スキャンと同じく行を順に選局した時間だけを測った
- 5つの受信機の同時受信と長時間の録画
- PX-MLT8PE・DTV02A-5TS-P・DTV02A-4TS-P と、イッツコム以外の回線

## 隣の受信機の開閉による 256QAM の誤り

J.83 Annex B の利用者から、J.83 Annex B で受信中にほかの受信機を開くと、先に開いていた受信機にドロップが出て、ランダムではなく同じ受信機に出るという報告がありました。  
この環境には J.83 Annex B の信号がないため、同じ 256QAM で同程度のビットレート (約34Mbps) の UHF 20ch (ISDB-C) で再現を試みました。

### 再現した条件

受信機 0〜2 で UHF 20ch を受信している間に受信機 3 を開いて選局すると、受信機 2 にだけ TEI 付きのパケットと CC の誤りがまとまって出ました (8回中8回、1回あたり TEI 約15件)。  
誤りは、受信機 3 の最初の選局と、受信機 3 を閉じたときに出て、開いたまま同じチャンネルへ選局し直したときには出ませんでした。  
受信機 3 を地デジで選局しても同じく出たため、ケーブルの選局の処理ではなく、受信機 3 のチューナーが待機と動作を切り替えることが引き金です。  
受信機 1 を開いたときに受信機 0 に出る組み合わせもあり、どの受信機に出るかは開く受信機ごとに決まっていました。

### 影響を受ける受信

地デジや BS/CS の受信でも同じことが起きるかを、変更前の版で調べました。  
受信機 0〜2 で同じチャンネルを受信している間に、受信機 3 を開いて2秒後に選局し、3秒ごとに2回選局し直してから閉じる操作を、受信側と受信機 3 の放送方式の組み合わせごとに繰り返しました (WinUSB 版は9通り × 5回、Linux 版は9通り × 4回)。

| 受信側 | 受信機 3 | WinUSB 版 | Linux 版 |
|---|---|---|---|
| 地デジ 27ch | 地デジ・BS・ケーブル | 15回中0回 | 12回中0回 |
| BS15 | 地デジ・BS・ケーブル | 15回中0回 | 12回中0回 |
| ケーブル UHF 20ch (256QAM) | 地デジ | 5回中4回 | 4回中4回 |
| ケーブル UHF 20ch (256QAM) | BS | 5回中1回 | 4回中1回 |
| ケーブル UHF 20ch (256QAM) | ケーブル C52 | 5回中4回 | 4回中3回 |

表の回数は、受信機 3 の操作と同じ時刻に受信側へ誤りが出た回数です。  
地デジの受信側には、受信機 3 を開く前の、自分の選局の直後に TEI だけの誤りが出た回が両方の版でありましたが、受信機 3 の操作とは時刻が合わないため数えていません。  
受信側が 64QAM の C52 のときも、誤りは出ませんでした。

この誤りは、256QAM のケーブルを受信しているときにだけ表に出ます。  
地デジと BS/CS では、変更前の版で隣の受信機の開閉による誤りは出ていません。

### 原因と対処

PX-MLT5PE は、1つの地上波・ケーブルの RF 入力を全チューナーへ分配していて、チューナーは既定の待機状態で RF 入力の整合を保ちません。  
Sony のチューナーのコードには、待機中も整合を保つ設定 (`SONY_HELENE_CONFIG_POWERSAVE_TERR_RFIN_MATCHING`) があり、これを使うと、受信機 3 の選局と閉じる操作で受信機 2 に誤りが出なくなりました。  
整合が変わることで分配先の隣のチューナーの入力が一瞬乱れる、というのが現時点の見立てで、この設定で誤りが消えたことと矛盾しません。  
PLEX の公開ドライバーも既定の待機状態を使っているため、公式ドライバーでも同じことが起きている可能性があります。

この設定だけでは、電源を入れた直後の状態から待機へ切り替える最初の初期化で整合が変わり、受信機を開いたときに隣の受信機へ誤りが出ました。  
そのため、まだ初期化していないチューナーを、256QAM の受信が始まる前にまとめて待機状態へ初期化します。  
この初期化を電源投入のたびに行うと、地デジと BS/CS だけを使う場合でも、最初の1台を開く時間が約 0.3 秒から約 1.1〜1.4 秒に延びるため、電源投入から初めて ISDB-C を選局するときにだけ行うようにしました。  
初期化だけを残して整合の設定を戻すと、受信機 2 の誤りは3回中3回で再び出たため、誤りを止めているのは整合の設定です。

### 変更後の確認

上の組み合わせを変更後の版でも繰り返し、WinUSB 版・Linux 版とも、すべての組み合わせで受信機 3 の操作による誤りは0回でした (WinUSB 版は45回、Linux 版は36回)。

地デジと BS/CS の開く時間と選局の時間は、変更前の版と交互に測って同じでした。

| | WinUSB 版 (各12回) | Linux 版 (各4回) |
|---|---|---|
| 開く時間 | 変更前 約 0.29 秒、変更後 約 0.30 秒 | 変更前・変更後とも約 0.29 秒 |
| 地デジの選局 | 変更前 0.97 秒、変更後 0.98 秒 | 変更前 0.99〜1.03 秒、変更後 0.98〜1.01 秒 |
| BS の選局 | 変更前 0.16 秒、変更後 0.16 秒 | 変更前 0.27〜0.28 秒、変更後 0.27 秒 |

電源投入から初めての ISDB-C の選局は、ほかのチューナーを初期化する分だけ延びます (WinUSB 版で約 0.25 秒から約 0.87 秒、USB/IP を経由する Linux 版で約 0.42 秒から約 1.43 秒)。  
2回目以降の ISDB-C の選局は変更前と同じで、全受信機を閉じて電源が切れた後は、次に初めて ISDB-C を選局するときにもう一度初期化します。  
受信中の C/N も変更の前後で同程度で、カードリーダーを先に開いた状態での受信とカードの通信も、変更前と同じ結果でした。

### 未検証の範囲

- J.83 Annex B の実際の信号での効果 (報告と同じ症状かを含む)
- PX-MLT8PE・DTV02A-5TS-P・DTV02A-4TS-P (同じチューナーを使うため同じ設定を適用している)
- BS/CS の RF 入力の待機状態 (今回の誤りは地上波とケーブルの入力で起きたもので、BS/CS 側の設定は変えていない)

同じ利用者からは、J.83 Annex B で開いた後に全受信機を閉じてから開き直すと「チャンネル変更できません」になる (条件不明) という報告もありました。  
この環境では、J.83 Annex B の選局と停止の後に ISDB-C と地デジで開き直す操作 (8回)、同じプロセスで閉じて開き直す操作 (DriverHost の終了を挟む場合を含めて9回) のどれも成功し、再現していません。

## レビューを受けた見直し

ISDB-C 対応を、地デジと BS/CS だけの利用者への影響、公開する I/F の形、CATV の受信そのものの3つの観点で見直し、次のように変えました。

### 地デジと BS/CS だけの利用者への影響

チューナーの待機中に RF 入力の整合を保つ設定は、電源投入から初めて ISDB-C か J.83 Annex B を選局したときにだけ全チューナーで有効にし、それまでは PLEX の公開ドライバーと同じ既定の待機状態にしました。  
地デジと BS/CS では隣の受信機の開閉による誤りが変更前から出ておらず、弱電界での C/N や他の機種での影響も測っていないため、効果を確認した 256QAM の受信に限っています。  
閉じているチューナーはその場で初期化し直し、開いているチューナーは、I2C が開いている受信機の復調器と同じ経路を通るため、次に待機へ戻るときに設定を書き込みます。  
そのため、初めての ISDB-C の選局の時点で開いていたチューナーは、その後に一度だけ整合の変わる切り替えが起き、そのとき 256QAM を受信中の隣の受信機に誤りが出る可能性があります。

同梱の `BonDriver_PX-MLT.ini` は、ISDB-C と J.83 Annex B を有効にしない設定に戻しました。  
有効にすると、回線のない利用者でも EDCB のチャンネルスキャンで 534行の選局が加わり、信号のない行の失敗 (約 1.1 秒) と EDCB の再試行を合わせて、約24分長くなるためです。  
`DriverHost_PX4.ini` には ISDB-C と J.83 Annex B を書かず、PX-MLT 系の地上波を受信できる受信機に DriverHost が加えます。

### 公開する I/F の形

J.83 Annex B は、ISDB-C の系統の中のシンボルレートの値 (5600) で表すのをやめ、独立した放送方式 (`PTX_J83B_SYSTEM` 、WinUSB 版の `J.83B`) にしました。  
復調器が J.83B と ISDB-C を別の動作モードで扱い、Sony のコードも別の方式としているためで、ChSet も J.83 Annex B の中心周波数の行を別のファイルに分けています。  
拡張 ioctl は ISDB-C と J.83 Annex B だけで受け付け、構造体を 32 ビットと 64 ビットで同じ配置にし、`PTX_GET_CNR` は PX-MLT 系の地デジと同じく PT1/PT3 互換の値を返す形にしました。

### CATV の受信

TSMF の何本目の指定は、最初のヘッダーで相対 TS 番号に決め、受信中に事業者が有効な TS の組を変えても別の TS へ切り替わらないようにしました。  
ヘッダーが CRC の誤りで認識されないときも、ヘッダーの位置に PID 0x002f のパケットが届いていれば、そろった前のフレームを出力し、捨てるフレームを BonDriver_BDA と同じ1つにしています。  
stream_type が分割 TLV を示していても、分割 TLV 以外のパケットを運ぶ TS は MPEG-2 TS として出力し、Linux 版では低レートの TS を 200 ミリ秒ごとに `read()` へ渡すようにしました。

### 確認したことと未検証の範囲

Linux 版のビルド (WSL2 の 6.18 カーネル) と、WinUSB 版の x86 と x64 のビルド、`build.ps1` の模擬試験 (復調器とチューナーのレジスターの値、TSMF の分離、ChSet の読み込み) が通ることを確認しました。  
追加した模擬試験は、守っている処理を元に戻した版で失敗することも確認しています。  
この見直しの後の版では、実機での ISDB-C・J.83 Annex B・地デジ・BS/CS の受信、隣の受信機の開閉による誤り、EDCB のチャンネルスキャン、recisdb での受信を、まだ確認していません。  
recisdb は、J.83 Annex B の放送方式、`PTXT_TSMF_STREAM_PARAM` の番号、`struct ptxt_params` の配置、C/N の換算を、この版に合わせて変えています。

### J.83 Annex B の実際の信号の報告

J.83 Annex B の回線を持つ利用者から、見直しの前の WinUSB 版で TVTest のチャンネルスキャンを行い、受信できたという報告がありました。  
報告のチャンネル定義は20波 (112.75〜587.25MHz) で、どれも同梱のチャンネル定義の H04〜H08・H30〜H31・H36〜H39・H41〜H43・H60〜H61・H74・H76〜H77 と、H28 を +4MHz ずらした 272.75MHz の行に含まれていました。  
TVTest はそのうち15波で、スカパー！プレミアムサービスのネットワーク (ONID 10) の134サービス (試験チャンネルを含む) を見つけ、138.75・320.75・340.25・366.25・587.25MHz の5波ではサービスが見つかりませんでした。  
272.75MHz の搬送波では C/N 36.81dB・35.42Mbps で受信していて、ずれた周波数の行を置いた判断と矛盾しません。

その後、Digital Devices のドライバーがスカパー！プレミアムサービス光に使う表が、6.5MHz 刻みで 769.25MHz (H105) まで続き、H44 を +2.2MHz ずらした 374.95MHz も持つことが分かりました。  
同梱のチャンネル定義は H77 (587.25MHz) までで 374.95MHz もなかったため、H78〜H105 と 374.95MHz の行を加えました。

### PX-MLT8PE

PX-MLT8PE は、地上波のアンテナ端子が1つで、5チューナー側と3チューナー側の2つの USB デバイスが同じ入力を分けて使っていると考えられます。  
待機中の整合の設定と事前の初期化は同じ USB デバイスのチューナーにしか届かず、3チューナー側は電源を独立して入り切りするため、5チューナー側で 256QAM を受信中に3チューナー側の受信機を開閉すると、誤りが出る可能性があります。  
2つの USB デバイスの電源を連動させれば避けられますが、実機がなく、地デジと BS/CS の利用者の電源の扱いを変えることになるため、見送りました。

## 公開ドライバーとの関係

復調器とチューナーの ISDB-C の設定値は、PLEX の Linux ドライバーに含まれる Sony のコードを一次資料としています。  
このドライバーは `MODULE_LICENSE("GPL")` (GPL v2 以降) のカーネルモジュールとして公開されていて、このリポジトリのライセンス (GPL-2.0-only) で配布できます。  
J.83B の復調器の設定値は、Sony の手順を移した TBS の `cxd2878.c` (GPL-2.0-only) に基づいています。  
移した値の出所は、各ファイルの冒頭の著作権表示とコメントに書いています。
