# 2026年10月18日 ISDB-C 対応の取り込みと実機確認の記録

この文書は、PX-MLT 系のケーブルテレビ (ISDB-C) の受信に対応したフォークを取り込んだ経緯と、実機で確かめた結果、確かめられていない範囲をまとめたものです。  
使い方は [README](../README.md) の「ケーブルテレビ (ISDB-C) の受信」にあります。

## 検証環境

- Windows 11 (x64) に PX-MLT5PE を PCIe で接続し、WinUSB 版の DriverHost_PX4 と BonDriver を使用
- アンテナ端子には、イッツコムの CATV 回線をつないだ (地デジのパススルー・BS の IF・ISDB-C が同じ同軸ケーブルで届く)
- Linux 版は、同じ PX-MLT5PE を usbipd-win の USB/IP で WSL2 (Ubuntu 24.04) へ渡して確認した。USB/IP を経由するため、TS の誤りの数はネイティブ Linux の結果として評価していない
- 受信の確認には、BonDriver を直接読み込んで TS を保存する試験用のツールと、同期・TEI・PID ごとの CC・PAT の TSID・SDT のサービスを数えるスクリプトを使った

## 取り込んだもの

PX-MLT 系の ISDB-C 対応は、次のフォークで進められていました。

| フォーク | 内容 |
|---|---|
| [n0atl/px4_drv](https://github.com/n0atl/px4_drv) の `isdbc-edition` | Linux 版と WinUSB 版の ISDB-C (64QAM) の最初の実装 |
| n0atl/px4_drv の `feature/tsmf-tlv-v61` | WinUSB 版の 256QAM・TSMF の分離・生 TLV 出力 |
| [aoiro-labo/px4_drv](https://github.com/aoiro-labo/px4_drv) の `feature/tsmf-tlv-v61` | 上の版に、J.83 Annex B (5.6Msps) の受信と、ケーブル受信後のチューナー停止の修正を追加 |
| [nanamitm/px4_drv](https://github.com/nanamitm/px4_drv) の `develop` | macOS 版と上の版を統合し、公開ドライバー由来の参照プロファイルを追加 |

aoiro-labo 氏のブランチが、n0atl 氏の ISDB-C・TSMF・TLV のコミットと J.83B をすべて含んでいたため、これをマージで取り込みました。  
macOS 版は、このリポジトリの対象から外れるため取り込んでいません。

取り込みの際に、ISDB-C と関係のない変更 (ダブルクリック用のビルドスクリプト、INI の重複キーの扱い、Visual Studio の版の範囲) と、開発時の診断メモの文書を外しました。

## 取り込んだ後に直したこと

取り込み元のコードには、録画の失敗を成功と見誤る経路や、ISDB-C を使わない利用者にも影響する変更がありました。  
次の点を後続のコミットで直しています。

- BonDriver が、機種にかかわらず読み込まれるたびにログファイルを書き出していた。INI の `DebugLog` で有効にしたときだけ出力するようにした
- ISDB-C のロック確認のたびに、FEC などの診断の読み出しと合計 500ms の待ちが入り、診断の読み出しの失敗がロックの失敗になっていた。ロック確認は QAM の同期と TS ロックだけにした
- 存在しない相対 TS を指定したときや、256QAM の搬送波を 64QAM に固定して選局したときに、TS が届かないまま選局が成功していた。ロック後に USB からの入力と TSMF のヘッダーを確かめて、届かなければ選局を失敗にした
- ChSet の範囲外の値が、別の相対 TS の指定として扱われていた。範囲外の値の行を読み飛ばすようにした
- 生 TLV の出力で、壊れたパケットや同期の喪失のときに組み立て途中の TLV が残っていた。これらのときは捨てるようにした
- チューナーに 24MHz の水晶用の値 (REF_R) を書いていた。PX-MLT 系の 16MHz に合った値を書くようにした
- 配布する INI で ISDB-C が既定で有効になっていて、地デジと BS/CS しか使わない利用者でも null パケットの除去がブリッジから DriverHost へ移っていた。既定で無効にした

あわせて、TSMF の TS を TSID で指定する方式を足しました。  
TSMF の処理は、[radi-sh 氏の BonDriver_BDA](https://github.com/radi-sh/BonDriver_BDA) の `TSMF.cpp` と同じ組み立てで、ヘッダーの直後の52パケットを位置で数え、相対 TS の割り当てが一致するパケットだけを通します。  
取り込み元は相対 TS 番号での指定だけだったため、BonDriver_BDA の `TSMFMode=TSID` と同じく、ヘッダーの TSID の対応表から相対 TS 番号を求める指定を加えています。

## 確認できたこと

### 搬送波の走査

取り込み元の配布 ChSet (CATV・UHF・VHF の3空間) を順に3秒ずつ選局し、46の搬送波で選局できました。  
43の搬送波は、同期・TEI・CC の誤りが0件でした。  
誤りが出たのは VHF の 8ch (TEI 175件) と 12ch (TEI 99件) だけで、周波数の補正などの調整は行っていません。

受信できたのは、BS のトランスモジュレーション (NHK BS・WOWOW・BS11・BS12・BS フジなど)、地デジを ISDB-C に載せ替えたもの、ケーブル独自の専門チャンネル (J SPORTS・ディズニーチャンネル・CNN など) で、SDT から175のサービスの名前を読み出せました。  
選局に約 2.3 秒かかった搬送波は、64QAM を試した後に 256QAM で選局できたもので、多チャンネルの専門チャンネルが載っていました。

### TSMF

C52 の搬送波は TSMF で2つの TS が多重されていて、ヘッダーで有効な相対 TS は 0 (TSID 17488、ONID 4) と 14 (TSID 16895) でした。  
52のスロットのうち2つだけが相対 TS 14 に割り当てられていて、相対 TS 14 は毎秒約 115KB の低レートのストリームでした。

- 相対 TS 0 と 14 を指定すると、それぞれの TS だけを、CC の誤りなしで取り出せた
- 存在しない相対 TS (1〜3) を指定すると、選局が失敗する (取り込み直後の版では成功と返して0バイトだった)
- TSID 17488 と 16895 で指定しても同じ TS を受信でき、存在しない TSID では選局が失敗した

### 安定性

64QAM (C51 の NHK BS)・256QAM (UHF 20ch)・TSMF の相対 TS 0 (C52) の3搬送波を、別々の受信機で同時に5分間録画しました。  
3つとも同期・TEI・CC の誤りは0件で、最大の無受信時間は 117ms でした。  
C/N は 64QAM が 25.7〜27.7dB 、256QAM が 31.8〜33.8dB でした。

### 既存の受信

取り込んだ版で、地デジ (27ch の NHK 総合) と BS (BS15) を10秒ずつ受信し、誤りは0件でした。

### チューナーの水晶の値

チューナーに書く REF_R の値を 24MHz 用 (0x18) から 16MHz 用 (0x10) に変えた前後で、64QAM・256QAM・TSMF の4搬送波を30秒ずつ受信しました。  
C/N の差は ±0.4dB 以内で、誤りはどちらも0件でした。

Linux 版では、256QAM の搬送波を 64QAM の設定で選局したときの挙動が、この値で変わりました。  
24MHz 用の値では、復調器が2回とも誤ってロックを報告し、TS が1バイトも届かないまま選局が成功しました。  
16MHz 用の値では、3回とも同期が成立せず、選局が失敗しました。

### Linux 版

`experimental_isdbc=1` で読み込んだモジュールで、64QAM の C51 (NHK BS) を受信できました。  
復調器が検出した QAM は 2 (64QAM) で、公開ドライバーの定義と一致しました。  
TSMF の搬送波 (C52) では、2つの TS が多重されたまま出力されます。

## 確かめられていないこと

- PX-MLT5PE 以外の機種 (PX-MLT8PE・DTV02A-5TS-P・DTV02A-4TS-P) と、イッツコム以外のケーブルテレビ局
- 長時間の録画と、5つの受信機での同時受信 (取り込み元の作者は、生 TLV を含む5受信機の同時受信で約3分ごとに全受信機が同時に欠落したと報告していて、原因は分かっていない)
- J.83 Annex B (この回線に信号がないため、I2C の通信を模擬した試験だけで確かめた)
- 生 TLV の出力 (この回線で 4K の TLV が載った搬送波を探していない)
- 取り込み元が設けた TSMF の slot offset の必要性。radi-sh 氏の実装にはなく、取り込み元の文書・コミットにも理由がない。手元の回線では `0` で正しく分離できた
- ネイティブ Linux での受信

## 公開ドライバーとの関係

復調器 (CXD2856ER) とチューナー (CXD2858ER) の ISDB-C と J.83B の設定値は、Linux の `cxd2841er.c`・`helene.c` と、Sony 系の公開ドライバー ([koreapyj/cxd28xx](https://github.com/koreapyj/cxd28xx)、TBS の `cxd2878.c`) の値と照合できます。  
Linux の2ファイルと TBS の `cxd2878.c` は GPL-2.0-or-later 、koreapyj/cxd28xx は GPL-2.0-only で公開されていて、いずれもこのリポジトリのライセンス (GPL-2.0-only) で配布できます。  
移した値の出所は、各ファイルの冒頭の著作権表示とコメントに書いています。
