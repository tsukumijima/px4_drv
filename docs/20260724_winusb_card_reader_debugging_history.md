# 2026年7月24日 WinUSB 版内蔵カードリーダーのデバッグ記録

## この文書の役割

この文書は、WinUSB 版内蔵カードリーダーの初期実装で、実機に現れた症状をどのように切り分け、何をコードへ反映したかを記録します。  
最終的な試験結果の一覧は [`20260724_validation_record.md`](20260724_validation_record.md)、現行の保守規則は [`WinSCard_PX4/README.md`](../winusb/src/WinSCard_PX4/README.md) を参照してください。  
ここでは、後続作業が同じ誤診と不足した試験を繰り返さないため、途中で退けた仮説も残します。  

記録の基準は、`develop` ブランチの `f1c5a2cb7df824474b884e7a2006cb242baf0939` です。  
この HEAD 自体は BonDriver の終了処理を修正したコミットであり、本書に記録する切り分け結果には影響しません。  
2026年7月23日以降の ACAS 対応と外部 Issue の追加確認は、[`20260724_card_reader_work_index.md`](20260724_card_reader_work_index.md) から該当文書を参照してください。  

## 最初の起動確認

### `SCARD_E_NO_SERVICE` の切り分け

最初の実機試験では、TVTest が「スマート カード リソース マネージャーが実行されていません」と表示し、`SCARD_E_NO_SERVICE` を返しました。  
DriverHost_PX4 と WinSCard_PX4 の起動失敗に見えましたが、TVTest の TS プロセッサー設定が以前の特殊カードリーダー名を保持していたことが原因でした。  

新しく列挙された `Digibest ISDB2056 Smart Card Reader` または `PLEX PX-MLT5PE Smart Card Reader` を選択し、チャンネルを切り替えると復号できました。  
この経験から、カードサーバーが正常でも、アプリケーションが保存した旧リーダー名によって失敗が続くことを確認しました。  
WinSCard API の試験と TVTest の保存状態は、別々に確認する必要があります。  

### 物理カードの確認

DTV02A-1T1S-U、PX-MLT5PE、PX-W3U4 の各内蔵スロットへ B-CAS を挿し、個別のリーダー名と対応する BonDriver を組み合わせて確認しました。  
カードの向きや奥まで挿入されているかは、コードの問題を判断する前に実機で確認しています。  

PX-W3U4 は BS・CS のアンテナ線を接続していないため、受信確認は地上波だけです。  
この配線条件は、カード API が通ることと、PX-W3U4 の全放送方式を確認したことを区別するために残します。  

## チャンネル切り替え時のドロップ

### カード対応とは別に見つかった条件反転

ISDB2056 系で以前から報告されていたチャンネル切り替え直後のドロップを調べたところ、WinUSB 版の通常 TS 同期判定に条件反転がありました。  
連続する188バイト境界を走査するループが、同期バイト `0x47` を見つけたときに終了し、壊れた値を見つけたときに継続する実装になっていました。  

正しい条件は、`0x47` 以外を見つけた時点で連続区間を終了することです。  
ISDB2056 と ISDBT2071 の同型処理を修正し、PX4 と PXMLT のタグ付き TS を含む判定を [`driver/ts_sync.h`](../driver/ts_sync.h) へ共通化しました。  
`52563d58f839b1454936d5ef14832f073e280598` がこの変更です。  

残りバッファの長さも宣言時に初期化し、ストリーミング開始前の未定義値を次の受信へ混ぜないようにしました。  
Linux 版の同型処理は確認時点ですでに正しい条件だったため、条件反転の修正は WinUSB 版だけです。  

### 回帰試験

`ts_sync_condition_test` は、通常 TS の `0x47` と、チューナー番号を上位ビットへ持つタグ付き TS を実行値で検査します。  
ソース文字列を正規表現で探す試験は、同じ意味の書き換えや別の条件反転を正しく判定できないため、共通の副作用なし関数を C++ から直接呼ぶ形へ変更しました。  

`channel_switch_stress` は、選局ごとに前チャンネルのバッファと continuity counter を捨て、同期エラー、transport error、continuity error、空受信を記録します。  
adaptation field の長さが188バイト内に収まるかも確認し、試験器自身が破損パケットを範囲外参照しないようにしています。  

このバグは実際にチャンネル切り替え時の TS を壊す問題でしたが、後述する ISDB2056 の断続的なスクランブル増加とは別件です。  
後者では D と E が0のまま S だけが増え、TS 受信自体は連続していました。  

## カード抜去と再挿入

### ドライバが物理カードを使っていることの確認

PX-W3U4 のカードを TVTest で受信中に抜くと、既存の Ks が失効した数秒後からスクランブルが増えました。  
この挙動により、画面が別のソフトウェアカード実装で偶然復号されているのではなく、選択した内蔵スロットの B-CAS を実際に使っていることを確認しました。  

カードを再挿入すると、WinSCard_PX4 と DriverHost_PX4 は新しいカードを検出し、次の要求で ATR と T=1 セッションを作り直せます。  
ただし、当時の TVTest と TvCas は、カードリーダーを切り替えてチャンネルを変更するか、TVTest を再起動するまで復号を再開しませんでした。  
TS プロセッサーの有効・無効だけではカード接続を作り直さないため、復帰しません。  

### 上位層にあった再接続条件

当時の TvCas は、直前の ECM が成功していた場合だけ同じ ECM の再送と `ReOpenCard()` を試していました。  
カードが抜けた状態で再接続にも失敗すると成功状態が失われ、再挿入後の後続 ECM でカードを開き直す入口がなくなります。  

これは DriverHost_PX4 の再挿入検出だけでは解消できない、上位層の状態管理でした。  
[TvCas の `fb3e24b`](https://github.com/tsukumijima/TvCas/commit/fb3e24b035905366fb8aa1bbf0b87670a8b1f0d6) で、通信失敗後も間隔を空けてカードを再接続し、成功時に同じ ECM を再処理するよう修正しました。  
既存の ECM キューとカード処理スレッドを全面的に書き直さず、復帰条件だけを変更しています。  

ドライバと WinSCard_PX4 は、次の APDU が届いたときに復帰できる状態を提供します。  
アプリケーションが APDU を再送するか、カードを開き直すかは上位層の責務であり、両方の状態遷移を混同してはいけません。  

## ISDB2056 の断続的な復号停止

### 現象

同じ CATV 局のチャンネル (ch10) を ISDB2056 と PX-W3U4 で同時受信し、PX-MLT5PE でも別の BS を受信した条件で、ISDB2056 だけスクランブルパケットが断続的に大量増加しました。  
TVTest の表示は D 0、E 0のまま S だけが増え、同じチャンネルを受信した PX-W3U4 は S 0でした。  

カードを抜いた状態では確実に復号が止まり、差し直すと一度は復帰したため、ISDB2056 の内蔵カードを利用していることは確認できていました。  
接触不良だけでは、同じ機種でライブ受信中に繰り返し発生し、別機種では発生しない差を説明できませんでした。  

### 退けた仮説

同一 TS に含まれる非選択サービスを CasProcessor が意図的に復号せず、TVTest がそれを数えているという仮説は、S が一定値で止まらず断続的に増えた実測と一致しません。  
同じ ch10 を PX-W3U4 が S 0で復号したため、放送側の ECM やチャンネル固有条件も主な説明から外れました。  

D と E が0であることから、アンテナ、同期、continuity counter の問題をスクランブル増加の直接原因にはできません。  
TS 受信とカード UART は別の処理なので、TS が無傷でも ECM 更新時のカード通信だけが失敗する可能性を残しました。  

短時間の `SCardTransmit()` 成功は、問題がない証拠になりませんでした。  
障害は断続的で、ライブ TS と同じ USB ブリッジ上の UART が同時に動くときだけ発生したためです。  

### 保存済み TS の試験が不足した理由

捕捉済み TS を libaribb25 へ一気に渡し、ISDB2056 のカードで復号する単体試験は成功しました。  
この結果から分かるのは、カードと T=1 の基本通信が静かな条件で成立することだけです。  

保存済み TS の復号と別プロセスの受信を並行させても、TVTest と同じ ECM の到着時刻、BonDriver の読み出し、カード APDU の順序にはなりません。  
保存済み TS の試験では実際の受信条件を再現できないというメンテナの指摘を受け、以後の主な判定は「ISDB2056 の BonDriver から届いたライブ TS を、その同じ ISDB2056 の内蔵カードを使う libaribb25 へ直ちに渡す」一体試験へ変更しました。  

### CLI 一体試験

`live_b25_reliability` は BonDriver と libaribb25 を動的に読み込み、TVTest を開かずライブ TS を到着順のまま復号します。  
入力と出力のスクランブルパケット、同期エラー、ECM 処理数、`Decode()` の失敗回数と処理時間を同じ時系列で記録します。  

修正前の ISDB2056 では、ECM 更新時に3.320秒から3.331秒の停止が発生し、最大停止は6.573秒でした。  
2分間で3回再現し、libaribb25 が同じ ECM を再送すると最終的には復帰しました。  
TVTest で観察した、数秒単位の映像停止と大量の S 増加に一致する結果です。  

### 実際の原因

T=1 と UART の時系列を採取したところ、カードは29バイトの応答を返していましたが、DriverHost_PX4 がフレーム完成前の FIFO を読み出していました。  
失敗時の読み取り量は28/29バイト、17/29バイト、25+3/29バイトで、末尾の LRC を含む1バイトから12バイトを取り逃していました。  

IT9305E の `UART_RX_LENGTH` は受信途中でも増加します。  
長さが0より大きいことだけを待機条件にすると、ライブストリーミング中の制御転送の時刻によって、応答の途中を完成フレームとして読み出します。  
不完全な T=1 フレームは検証に失敗し、操作全体の3秒期限まで再送と再初期化が続くため、復号が数秒止まっていました。  

ISDB2056 だけで顕在化した理由は、同じ IT9305E 上で通常 TS のライブストリーミングとカード UART の制御転送が重なり、FIFO を途中で読む時間条件が生じたためです。  
PX-W3U4 と PX-MLT5PE でも誤った待機条件は共通していましたが、試験時の USB 構成と転送時刻では再現しませんでした。  
機種固有のカード接触問題ではなく、共通処理にある競合条件が ISDB2056 の負荷で表面化したバグでした。  

### 修正

`CardDevice` に `IsCardDataReady()` を追加し、IT930x の `UART_RX_READY` が立つまで FIFO を読み出さない契約へ変更しました。  
この契約を ISDB2056、ISDBT2071、PX4、PXMLT の機種別実装へ反映し、T=1 ブロックと ATR の双方で完成を待ちます。  

`UART_RX_READY` が立つ前に `ReadCardData()` を呼ばないことは、`smart_card_state_test` の模擬デバイスで回帰試験にしました。  
待機処理は `ReadAtr()` と `ReceiveBlock()` で同じ `WaitCardDataReady()` を使い、同じポーリング間隔、エラー伝播、絶対期限を維持しています。  

一時的に追加した詳細な診断ログと環境変数は、原因を確定して自動試験へ置き換えた後に製品コードから削除しました。  
公開コードへ特定の PC の絶対パスや調査用トグルを残さないという方針を守っています。  

### 修正後の実測

診断コードを外した最終 DriverHost_PX4 で、同じ ch10 を3分間ライブ受信し、その場で libaribb25 による復号を行いました。  
入力1,960,960パケット、入力スクランブル1,948,877パケットに対し、出力スクランブルは0パケット、`Decode()` 失敗は0回、200ms以上の遅延は0回でした。  

最大 `Decode()` 時間は94ms、TS 同期エラーは0、信号レベルは30.11でした。  
診断ありと診断なしの3分試験を各1回実行し、どちらも修正前の停止を再現しませんでした。  
この条件では、最大6.573秒だった停止が最大94msまで解消したことを確認しています。  

この3分試験は、長時間録画、全チャンネル、全 USB ホストコントローラーで同じ結果を保証するものではありません。  
確認済み範囲を越える条件は、[`20260724_validation_record.md`](20260724_validation_record.md) の未検証事項として扱います。  

## カードと TS の同時負荷

`card_stream_stress` は、BonDriver で受信しながら別スレッドの2つの PC/SC 接続から同じ内蔵カードへ B-CAS APDU を繰り返し送ります。  
カードの成功数と失敗数に加え、TS の同期エラー、transport error、continuity error を負荷前後で比較します。  

この試験はカード API の直列化だけでなく、カード通信が TS の読み出し時刻を壊していないかを見るものです。  
カードの応答が全て成功しても TS にエラーが増えれば不合格であり、TS が無傷でも APDU が失敗すれば不合格です。  

`live_b25_reliability` は実際の ECM 到着に従って復号するため、固定 APDU を連続送信する `card_stream_stress` と目的が異なります。  
前者は実運用に近い復号の継続性、後者は高いカード負荷と TS 受信の干渉を測ります。  
どちらか一方だけで、もう一方の条件を確認済みとして扱わないでください。  

## 外付けカードリーダーの確認

System32 の `WinSCard.dll` を後段へ接続した後、SCR33xx 系の外付けカードリーダーを内蔵3台と同時に列挙し、ANSI と Unicode の接続、ATR、APDU を確認しました。  
DriverHost_PX4 を置かない隔離ディレクトリでも外付けだけを列挙、接続できることを試験し、PX4 側が不在でも System32 の呼び出しが完結することを確認しました。  

保存済み TS の一括復号だけでは、外付けリーダーが放送速度へ追従できるか判断できません。  
最終的には BonDriver のリアルタイム受信中に外付けカードへ APDU を送り、復号後のスクランブルパケット数と処理時間を測る条件を採用しました。  

内蔵リーダーと外付けリーダーを同じ API へ統合したことで、System32 側のキャンセル状態を汚す問題も見つかりました。  
待機していない外付けコンテキストへ不要な `SCardCancel()` を送ると次の操作へキャンセルが残るため、System32 の待機が実際に進行している間だけ転送するよう修正しました。  

## WinSCard API のレビューで見つかった問題

実機で復号できる状態になった後も、コードレビューと API 試験を繰り返しました。  
画面が映ることだけでは、メモリ所有権、エラー値、キャンセル、コンテキスト解放の競合、長い名前とバッファ境界を確認できないためです。  

レビューで修正した主な種類は、次のとおりです。  

- WTX と再送で処理時間が無期限に延びない絶対期限
- TA2 と TC2 を T=1 の IFSC と EDC に誤用しない ATR 解析
- T=1 CRC の上位バイトから下位バイトの順序
- USB 切断時のカードセッションと共有電源参照の破棄
- カードリーダーを持たない機種の公開 API 入口での拒否
- `SCARD_AUTOALLOCATE` の割り当て元と `SCardFreeMemory()` の対応
- System32 と PX4 のコンテキストを同時に扱うキャンセルと解放
- WinSCard API と同じ入力値エラー、プロトコル不一致、無効コンテキストの返却
- 名前付きパイプで固定長を越えるリーダー名を扱う場合の拒否
- テスト内で先行する失敗を後続の成功で上書きしない結果集計

外部レビューの指摘は、現在のコードに同じ条件が残っているかを確認してから採用しました。  
単なる重複削減や大規模な書き直しは行わず、実際の契約を壊す箇所だけを小さく修正しています。  

## 仮説の扱いから得た注意

### 接触不良を先に結論にしない

カードの向きと挿入状態は確認項目ですが、特定機種だけで D 0、E 0、S 増加が繰り返される現象を接触不良だけで終わらせると、共有処理の時間条件を見逃します。  
カード検出、ATR、T=1 フレーム長、LRC、APDU の時刻を残し、どこで失敗したかを分けて判断する必要があります。  

### 短時間の正常を断続障害の否定に使わない

API テストで数回の APDU が成功しても、数分に1回の失敗は検出できません。  
発生頻度に合わせた試験時間を確保し、正常時と失敗時の処理時間を同じ形式で採取します。  

### アプリケーションの表示だけで層を決めない

TVTest の S 増加は、カード通信、復号器の ECM 再試行、カード選択、アプリケーションの再接続状態のいずれでも発生し得ます。  
D と E、別リーダーでの同一 TS、保存済み TS、ライブ受信、直接 APDU を組み合わせて、失敗する層を絞ります。  

### 実運用の同時性を試験へ含める

カード単体で通る試験と、ライブ受信中に通る試験は別物です。  
同じ USB ブリッジ、同じ BonDriver、同じカード、実際の ECM 到着順を含む試験を主な証拠とし、保存済み TS と固定 APDU は原因を分ける補助試験として使います。  

## 後続作業への接続

現在の自動試験と実機試験の使い分けは [`WinSCard_PX4/README.md`](../winusb/src/WinSCard_PX4/README.md) に記載しています。  
2026年7月24日時点で実行した試験の数値、機種、アンテナ、カード配置、未確認条件は [`20260724_validation_record.md`](20260724_validation_record.md) を参照してください。  

Linux 版へ移る際も、`UART_RX_LENGTH` が増えたことを完成通知として扱わず、`UART_RX_READY` を待ってから読み出す契約を維持します。  
T=1 の状態機械を模擬 I/O で試験し、対象機器のライブ TS とカード UART を同時に動かす実機試験までを完了条件にしてください。
