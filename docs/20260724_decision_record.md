## メンテナの判断意図

### 録画の安定性をカード機能より上位に置く

内蔵カードリーダーが利用できることは追加機能であり、既存の TS 受信を不安定にしてまで採用するものではありません。  
数パケットの欠落も録画結果へ残るため、カード APDU の成功と同時に D、E、S、空受信を確認するよう求めています。  

この意図から、カード単体の通信成功、短時間の映像表示、別フォークでの動作報告だけを完成条件にしていません。  
電源、USB 制御転送、ロック、機器寿命へ触れる変更は、カードと TS の同時負荷まで確認します。  

### 外部差分を権威として扱わない

Issue 投稿者、フォーク作者、他の LLM が作ったコミットのいずれも、由来だけで採用しませんでした。  
現行コードに同じ条件が存在するか、修正が現在の所有権と状態遷移に合うか、実測がどの範囲を支えるかを独立に確認します。  

この意図は、外部実装を否定するためのものではありません。  
先行実装から通信手順と実機情報を得ながら、現在の px4_drv が必要とする長時間受信、共有電源、ホットプラグ、エラー通知へ適合させるためのものです。  

### Windows で確認できることを Linux へ先送りしない

Windows 版と Linux 版は IT930x の共通処理を共有するため、Windows 側で確認できるプロトコルと境界値を先に固定します。  
Linux 実機が必要な項目だけを Linux 開発マシンへ引き継ぎ、Windows でも確認できる未実装や未試験を残さない方針です。  

この意図から、ACAS の状態試験、254バイト APDU、外付けリーダー未接続、Visual Studio プロジェクト単体のパス、3機種の TS 同時負荷まで Windows 側で処理しました。  
Linux 側へ渡すのは、カーネルビルド、Linux 固有の機器寿命、PC/SC IFD ハンドラー、Linux 実機の B-CAS と ACAS です。  

### 確認した事実と未確認の条件を混ぜない

メンテナが必要としているのは「概ね動く」という評価だけではなく、どの機種と条件で確認したかを後から追える記録です。  
試験できない条件は失敗とも成功とも扱わず、理由とともに未確認へ残します。  

PX-W3U4 の BS と CS、Windows 上の ACAS 実カード、外付けリーダーの最新回帰、Issue 投稿者の長期稼働を別項目にしたのはこのためです。  
長期確認を Issue 投稿者へ依頼する判断も、実装完了と Issue 完全解決を区別する意図に基づきます。  

### 将来の作業者へ判断をやり直させない

コードだけでは、なぜ同じ初期化順へ統一しなかったか、なぜブランチ全体を取り込まなかったか、なぜ追加の受信機ソートを見送ったかを復元できません。  
採用理由、棄却理由、検証範囲を日付付き文書へ残し、後続作業者が同じ調査を繰り返さない状態を目標にしています。  

この文書は、その意図を保存する判断記録です。  
恒久仕様が変わった場合も、当時の記録を上書きせず、新しい日付の文書から変更理由を接続します。  

## 開発全体の優先順位

### TS 受信を既存機能として守る

内蔵カードリーダー対応の目的は、B-CAS と ACAS の APDU が通ることだけではありません。  
同じ IT930x を使う TS 受信を停止させず、同期エラー、transport error、continuity error、空受信を増やさないことを同じ完成条件にしました。  

この判断は、カード通信も TS 受信も IT930x の制御転送を使い、直接には無関係に見える UART 操作が受信時刻へ影響し得るためです。  
カード単体の試験成功だけで採用する案は棄却しました。  

後続作業では、カード機能を変更した場合も、TS と APDU の同時負荷を試験します。  
Linux 側も同じ完成条件を使います。  

### Windows 実装を Linux の設計元として固定する

Linux 版の内蔵カードリーダーへ進む前に、Windows 版の状態機械と共通 IT930x 操作を固定する方針を採用しました。  
Linux と Windows は [`driver/it930x.c`](../driver/it930x.c) と [`driver/it930x.h`](../driver/it930x.h) を共有するため、Windows 側の未解決事項を残したまま Linux 側へ進むと、共通層の契約が途中で変わります。  

2026年7月24日時点では、Windows 開発環境で実装可能な既知のカードリーダー修正は残っていないと判断しました。  
この判断は、全機種と長期稼働を確認済みという意味ではなく、現行コードから導ける修正と、Windows 検証環境で実行できる試験を完了したという意味です。  

Linux 実装は、現在の [`smart_card.cpp`](../winusb/src/DriverHost_PX4/smart_card.cpp) をプロトコルの基準にします。  
yyya-nico 氏や makeding 氏の状態機械へ置き換える案は採用しませんでした。  

## ACAS 対応

### 名称を ACAS に統一する

カードと対応方式の名称は **ACAS** と表記します。  
`A-CAS` はこの作業で採用する名称ではなく、コードコメント、コミットメッセージ、文書を ACAS に修正しました。  

後続作業でも、既存の ACAS 表記を別表記へ戻さないでください。  
外部資料の原文を引用する場合だけ、原文の表記を維持します。  

### ATR が示す通信条件を使う

ACAS 対応では、製品名や ATR の固定一覧でカードを分類する方式ではなく、ATR の TA1 が `0x13` の場合に38400bpsを選び、TA3、TB3、TC3 から IFSC、BWI、EDC を取得する方式を採用しました。  

この方式なら、カードが示した T=1 の通信条件を適用でき、B-CAS 互換機能を持つ ACAS を WinSCard API 層で独自のカード種別へ変換する必要がありません。  
製品コードへ B-CAS と ACAS の ATR 許可一覧を追加する案は棄却しました。  

[`bcas_atr.hpp`](../winusb/src/WinSCard_PX4/bcas_atr.hpp) にある ATR は、実機試験で外付けカードへ B-CAS 固有 APDU を送らないための判定材料です。  
リーダー列挙や `SCardLocateCards*()` の製品仕様として使うものではありません。  

### B-CAS と ACAS の初期化順序を分ける

B-CAS は RESYNCH の後に IFS を送ります。  
ACAS は IFS から開始し、最初の IFS がタイムアウトまたは形式エラーになった場合だけ RESYNCH と IFS を再送します。  

両者を同じ初期化順序へ統一する案は採用しませんでした。  
makeding 氏の PX-Q3U4 と ACAS の実測、および Windows 側の状態試験が、この順序差を必要な互換処理として支えています。  

### APDU を UART 上限で分割する

254バイトの APDU を単純に拒否する案は採用しませんでした。  
LRC 使用時はヘッダー3バイトと LRC1バイトを含めると258バイトになり、IT930x の255バイト上限を超えるため、251バイトと3バイトの I-block へ分割します。  

CRC 使用時の INF 上限は250バイトです。  
カードの IFSC が大きくても、UART フレーム上限から計算した INF 上限を超えないことを契約にしました。  

この修正は `09836a961612fa6a7f52d30fe66c114cf6e0869e` に分離してコミットしました。  
境界値を単に入力検証で拒否すると、T=1 が本来提供するチェーン送信を使えず、ACAS の正常な APDU を処理できないためです。  

## T=1 の状態と時間制限

### 操作全体の絶対期限を維持する

APDU 全体の期限は3000msとし、再試行や WTX のたびに作り直さない方式を採用しました。  
ブロック単位の待機は500msを下限に BWI から計算し、操作全体の期限を上限にします。  

各再試行で相対タイムアウトを作り直す案は、カードが WTX を送り続けた場合や同じ異常応答を繰り返した場合に、呼び出しが無期限化するため棄却しました。  
状態試験には、WTX が続いても5秒未満で失敗する症例を入れています。  

Linux 側へ移植する場合も、カーネルの待機とユーザー空間の再試行を合算した操作全体の期限を維持します。  

### 失敗時にセッション全体を破棄する

カード抜去、USB 切断、転送失敗、プロトコル違反、時間切れでは、ATR、IFSC、CRC 設定、ブロック待機時間、送受信連番をまとめて初期値へ戻します。  
一部のフラグだけを無効にする方式は採用しませんでした。  

古い連番や ATR が残ると、再挿入した別カードや USB 再接続後の機器へ以前の状態を適用するためです。  
次の APDU はカード検出とリセットから再開します。  

形式不正 ATR に対するカードリセットは1回だけ再実行します。  
USB 転送エラー、未挿入、対応外 TA1 まで同じ再試行へ含める案は、失敗の意味を失うため採用しませんでした。  

### プロトコルとハードウェア操作を分ける

Windows 版では、`SmartCard` が ATR と T=1 を担当し、`CardDevice` がカード検出、リセット、UART 送受信、ボーレート変更を担当します。  
この分割を Linux 側でも維持する判断を採用しました。  

Linux カーネルへ T=1 の状態機械をすべて置く案は、模擬 I/O による試験が難しくなり、長い待機が TS と同じカーネル内へ入るため採用しませんでした。  
Linux カーネルは物理デバイス、排他、電源、USB 切断時の寿命を担当し、PC/SC IFD ハンドラー側が T=1 を担当します。  

## WinSCard API とリーダーの共存

### 内蔵リーダーを先に列挙する

WinSCard_PX4 をアプリケーションへ配置した場合、内蔵リーダーを先に列挙し、System32 が管理する外付けリーダーを後へ追加する順序を固定しました。  
libaribb25 など先頭の利用可能なリーダーを選ぶ実装で、内蔵カードを選びやすくするためです。  

この順序を設定項目にする案は採用しませんでした。  
互換 DLL を配置する操作自体を、内蔵リーダーを利用する意思として扱います。  

### 外付けリーダーの標準動作を System32 へ委ねる

外付けリーダーと、内蔵リーダーを統合する必要がない WinSCard API は、System32 の `WinSCard.dll` へ転送します。  
Windows の入力検証、ANSI 変換、メモリ所有権、エラーコードを独自実装で再現する範囲を増やさないためです。  

内蔵リーダーだけを扱う互換 DLL として System32 側を隠す案は、外付けリーダーを利用できなくするため棄却しました。  
内蔵リーダーと外付けリーダーは、同じアプリケーションから共存できる契約です。  

### 外付けリーダーがない試験を明示的にスキップする

外付けリーダー未接続を `winscard_api_test` 全体の失敗にしない判断を採用しました。  
PX4 内蔵リーダーの API 試験は継続し、System32 側の物理リーダーが必要な項目だけを `external_reader_tests=skipped (no system smart card reader)` と記録します。  

外付けリーダーがないことを理由に内蔵リーダー試験まで省略する案も、実行していない外付けリーダー向け試験を成功したように扱う案も採用しませんでした。  

この変更は `9eebc4d22b88b2f7cee07bd6bb255ff4901b77ca` です。  

## 機種と共有電源

### カードとチューナーを同じ基板電源の利用者として数える

カードリーダーを開いている間は、チューナーを使用していなくてもチューナー側基板電源を維持します。  
チューナー使用中にカードを閉じた場合も電源を維持し、最後の利用者が閉じたときだけ停止します。  

カード利用とチューナー利用を別々の真偽値だけで管理する案は、片方を閉じた時点で他方が使用中でも電源を停止する可能性があるため採用しませんでした。  
複数インターフェース機器では、同じ筐体に属するデバイス間でも利用数を共有します。  

### 初期化失敗時に取得した電源を戻す

カードまたは受信機の初期化が失敗した場合は、その処理が取得した電源利用数を戻します。  
エラーを返すだけで電源利用数を残す案は、以後の未使用状態でも基板電源が停止しなくなるため採用しませんでした。  

Linux の ISDB2056 は `2559c7b34b0739802d5f716152600448aa11a4f9`、PX4 複数デバイスの参照寿命は `2d96544e1d5ee33479451ac9b2e4553a2e379062` と `5cc2e7b94fa831fa8dc656dba02720daf6bdf097` で修正しました。  
Linux 実機での確認は残っています。  

### 未使用の PX4 基板電源を初期化後に停止する

Issue #36 に対して、初期化を終えた未使用の PX4 系チューナー側基板電源を停止する修正を Windows と Linux の双方へ入れました。  
Windows は `a28d48e1cf377115313bfbc925579ec231dc4ec8`、Linux は `ed28d77137f3f61ee3aac2fa3e6467028579f1af` です。  

停止するのはチューナー側基板電源であり、USB ブリッジの IT930x 自体は給電されたままです。  
IT930x のファームウェアが失われるという仮説は、実装と電源系統に一致しないため棄却しました。  

Windows 検証環境の3機種では、この変更後も通常受信とカード通信が成功しました。  
Issue 投稿者と同じ複数 PX4 筐体の条件、および Linux 実機は未確認です。  

## Issue #38 の扱い

### 単一原因へ決め打ちしない

`no receivers available` は、受信機を取得できない複数の内部状態を同じ表示へ集約します。  
Issue #38 を単一の再現原因へ結び付けず、コード上で独立して妥当性を確認できた4件を別々に修正しました。  

- `f108339027ca7aec0ad61c2946af359ec29cd894`：ReceiverManager の GUID 比較と排他制御
- `93ab9f2fff4795064568c85fe52c41c55c3e735a`：USB シリアル番号を実際の転送長の範囲で解析
- `e5ac32d4e9e3e3d772f9d2394897be41e3e01e96`：BonDriver 再オープン時の終了イベントを初期化
- `58d7cc95f17402fff6b0723a4c0b0c91bc6dee3e`：TS 転送開始失敗を呼び出し元へ返却

これらはコード上の欠陥として個別に修正する価値があります。  
一方、どの修正が Issue 投稿者の長期稼働時の現象へ一致するかは確認できていません。  

### Issue 番号だけをコミットメッセージへ付ける

Issue に関連する修正は、コミットメッセージの末尾へ `(#38)` のように番号を付けます。  
Issue 投稿者の条件で完全解決したと確認できるまで、`Close #38` と書ける段階にはないためです。  

同じ理由で、Issue #36 も複数筐体を含む投稿条件を確認するまでは自動クローズの対象外です。  
関連性と完全解決を別の事実として記録するための判断です。  

### 長期稼働確認を Issue 投稿者へ依頼する

Windows 開発環境ではコードから導ける修正と通常時の実機試験まで実施し、長期稼働での再発確認は Issue 投稿者へ依頼します。  
この待機は、Linux 実装へ進む前に片付けるべき未完了作業には当たりません。  

ただし、長期確認待ちを理由に Issue #38 を解決済みと表現することも避けます。  
現時点の表現は「論理的に妥当な修正を実装し、Windows 検証環境の通常受信でデグレードを確認していない」です。  

## PX-W3U4 の T1 から T0 へのドロップ

### PR #2 の通常選択順を維持する

[PR #2](https://github.com/tsukumijima/px4_drv/pull/2) が導入した通常選択順は、Windows 検証環境の PX-W3U4 でも T0 を T1 より先に選びました。  
このため、ReceiverInfo の番号を新しい比較キーとして追加する変更は見送りました。  

現在の順序がヒープ配置だけへ依存している可能性は論理上残ります。  
しかし、通常構成で期待順を実測でき、追加の並べ替えが既存の機種選択へ影響するため、再現条件のない予防変更は採用しませんでした。  

### 強制指定で干渉条件を分けて確認する

T1 を明示指定してから T0 を開くと、既知の T1 から T0 へのドロップを再現できました。  
これは PR #2 の通常選択を迂回して問題条件を意図的に作った試験であり、PR #2 が無効になった証拠にはなりません。  

Linux の現在のデバイス順は、同一グループ内で T0 が `/dev/px4video2`、T1 が `/dev/px4video3` です。  
Mirakurun の定義も T0 を先に並べる運用を推奨しますが、T1 使用中に T0 しか空いていない場合まで禁止するものではありません。  

ハードウェア内部の干渉そのものをドライバだけで完全に消せるとは判断していません。  
順序制御は、通常利用で問題条件を踏む頻度を下げる修正として扱います。

### 未コミット差分を実装者自身がレビューする

実装を終えた時点で、別のレビュアーへ渡す前に未コミット差分を実装者自身が読み直すことを必須にしました。  
今回も `origin/develop` との比較から、UART フレーム上限、参照寿命、ビルドパス、改行混在のように、局所試験だけでは見落とす問題を追加で発見しました。  

レビューでは、基準コミット `185aa1329ee6b04d9456917db65a767d0f690fcf` からの全差分、ステージ済み差分、未ステージ差分を分けて確認します。  
改行変換が疑われる場合は `git diff --ignore-space-at-eol` と `git ls-files --eol` を先に使い、行数だけから意味変更を推測しません。  

セルフレビューで見つけた独立した問題は、元の大規模実装へ混ぜて履歴を書き換えず、問題ごとに修正と試験を追加します。  
試験が通ったことは、差分全体が正しいことの保証にはなりません。  

最終確認では、`BonDriver::Term()` が終了イベントを閉じた後も `quit_event_` に古いハンドル値を残す問題を追加で修正しました。  
デストラクターなどから終了処理が重複した場合に同じハンドルを再度閉じる状態を避ける変更で、コミットは `f1c5a2cb7df824474b884e7a2006cb242baf0939` です。  

## 実機試験の解釈

### Windows 検証環境の3機種を正常受信の基準にする

Windows 検証環境へ接続した PX-MLT5PE、DTV02A-1T1S-U (ISDB2056)、PX-W3U4 の3機種で、内蔵リーダー列挙、カード APDU、TS とカードの同時負荷、保存 TS の復号を確認しました。  
この結果から、今回の修正後に通常受信を一律に壊すデグレードは確認されていないと判断しました。  

5分間の同時負荷で失敗が0件だったことは、長期稼働の無故障を証明しません。  
短時間の正常動作と、Issue 投稿者の長期再発確認を分けて扱います。  

### 放送休止を選局失敗へ数えない

受信試験中、あるチャンネルを受信できなかった試行がありましたが、時刻を確認すると放送休止時間と一致していました。  
この試行はドライバの選局失敗や `no receivers available` の再現には数えていません。  

今後も、空受信を記録する場合は試験時刻と放送状況を確認します。  
チャンネル番号だけで正常信号が存在すると仮定しないためです。  

### PX-W3U4 の BS と CS を今回の必須条件から外す

Windows 検証環境には衛星波のアンテナがなく、PX-W3U4 の BS と CS を試験していません。  
Linux 側と他環境で受信実績があるため、Windows 内蔵カードリーダーを固定するための追加試験から外しました。  

これは PX-W3U4 の BS と CS を Windows 検証環境で確認済みと扱う判断ではありません。  
今回のカード変更が触れた条件と、物理配線がなく試験できない既存受信条件を分けたものです。  

## Windows 側の完了範囲

2026年7月24日時点では、Windows 版を Linux 実装の設計元として使えると判断します。  
現行コードの状態遷移、共通 IT930x API、WinSCard API 試験、Windows 検証環境の3機種による通常受信とカード同時負荷に、既知の未実装修正は残っていません。  

この判断から除外する条件は、Windows 上の ACAS 実カード、Windows 検証環境にない対応機種、外付けカードリーダー実機との最新回帰試験、Issue #36 投稿者と同じ複数 PX4 筐体、Issue #38 の長期稼働です。  
除外条件は実装を止める残件ではなく、確認できる環境が得られた際に追加する検証項目です。  

Linux 開発マシンへ引き継ぐ実装作業は [`20260724_linux_card_reader_handover.md`](20260724_linux_card_reader_handover.md) を正本とします。
