# 2026年7月24日 WinUSB 版内蔵カードリーダー実装の成立記録

## この文書の役割

この文書は、WinUSB 版 px4_drv で内蔵カードリーダー対応を成立させるまでに、何を問題と捉え、どの設計を選び、どの案を採用しなかったかを記録します。  
現行コードの API 契約と保守規則は [`WinSCard_PX4/README.md`](../winusb/src/WinSCard_PX4/README.md)、2026年7月24日時点の採否は [`20260724_decision_record.md`](20260724_decision_record.md) を基準とします。  
ここでは、それらの文書だけでは失われる初期要件と設計成立の理由を扱います。  

記録の基準は、`develop` ブランチの `f1c5a2cb7df824474b884e7a2006cb242baf0939` です。  
この HEAD 自体は BonDriver の終了処理を修正したコミットであり、本書に記録するカードリーダー設計の採否には影響しません。  
同時進行した後続作業の内容は、[`20260724_card_reader_work_index.md`](20260724_card_reader_work_index.md) から該当文書を参照してください。  

## 出発点

### WinUSB 版に残っていた欠落

Digibest 製チューナーの内蔵カードリーダーは、独立した USB CCID 機器として PC に接続されていません。  
IT9305E 系の USB ブリッジを介し、GPIO でカードを検出し、専用の制御コマンドから UART を操作してカードと通信します。  
そのため、WinUSB を割り当てただけでは Windows のスマートカードリーダー一覧に現れず、System32 の `WinSCard.dll` から利用できません。  

公式 Windows ドライバは BDA カーネルドライバとしてチューナーとカードリーダーを扱っていたため、カード操作も BDA の独自制御を経由していたと推定しました。  
この部分は公開された公式仕様で確認できた事実ではなく、機器構成、既存ソフトウェア、公式ドライバの挙動を組み合わせた推定です。  
本実装では公式ドライバの逆解析を主要な根拠にせず、公開されているベンダー由来コードと実機の応答を優先しました。  

WinUSB 版 px4_drv は、USB 機器をユーザー空間の DriverHost_PX4 が管理するため、公式カーネルドライバの不安定さやカーネルクラッシュを避けられます。  
一方で、内蔵カードリーダーを使う入口が存在せず、物理スロットへ正規契約済みの B-CAS を挿しても利用できない状態が長く残っていました。  
アプリケーションローカルの別実装 `WinSCard.dll` で復号できても、内蔵スロットのカードを使えないという問題は解決しません。  

### メンテナが示した完成条件

最初から求められたのは、カードから APDU の応答を得るだけの実証ではありませんでした。  
数時間から数日間の録画で TS にドロップやベリノイズを発生させず、既存の BonDriver、DriverHost_PX4、複数チューナー、ホットプラグの挙動を維持したまま導入することが完成条件でした。  

Windows 検証環境に用意できた機種は PX-MLT5PE、DTV02A-1T1S-U の ISDB2056、PX-W3U4 です。  
実装範囲はこの3機種に限定せず、WinUSB 版が扱う機種のうち内蔵カードリーダーを持つ全機種へ広げ、未所持機種はコードと自動試験まで、実機確認は後続作業として区別する方針でした。  

PX-MLT8PE については、5チューナー側と3チューナー側の2つの USB デバイスが1つの筐体に収まっています。  
コード上の `PXMLT8PE3` は3チューナー側を識別する名前であり、独立した製品として扱わないことも、この時点で明示されました。  

## 参照した実装

### ベンダー由来の Linux ドライバ

[soralis0912/it930x_driver_native](https://github.com/soralis0912/it930x_driver_native) は、Digibest から一度だけ開示された Linux ドライバのソースとして提供されました。  
コード全体の構造や品質を採用する対象にはせず、IT930x の GPIO、UART、カードリセット、ボーレート設定に使う制御コマンドを確認する一次資料として使いました。  

この資料の価値は、公式 Windows ドライバを逆解析しなくても、機器が受け付ける低水準の通信手順を追える点にあります。  
カード通信の状態管理や公開 API は別途設計し、ベンダーコードの待機、エラー処理、共有状態をそのまま移していません。  

### yyya-nico 氏のフォーク

[yyya-nico 氏の develop ブランチ](https://github.com/yyya-nico/px4_drv/tree/develop) は、Linux から内蔵カードへ実際に通信できることを示した先行実装です。  
通信可能性の実証と、ベンダー由来コマンドを px4_drv へ接続する箇所の把握に役立ちました。  

ただし、ATR を3バイト以上で完了扱いする処理、T=1 フレームの完全性検証、再送と WTX、複数リーダーの識別、USB 抜去後の復帰には、長時間利用へそのまま採用できない条件がありました。  
この評価はフォーク全体を否定するものではなく、通信手順の資料として採用し、状態機械と PC/SC 接続は作り直すという判断です。  
Linux 側へ引き継ぐ具体的な差は [`20260724_linux_card_reader_handover.md`](20260724_linux_card_reader_handover.md) に記録しています。  

### 既存の Windows 実装

[BonDriver_BDA](https://github.com/radi-sh/BonDriver_BDA)、[BDASpecial-IT35](https://github.com/radi-sh/BDASpecial-IT35)、[TvCas](https://github.com/tsukumijima/TvCas)、[CasProcessor](https://github.com/tsukumijima/CasProcessor)、[libaribb25](https://github.com/tsukumijima/libaribb25) から、DTV アプリケーションが WinSCard API をどのように呼ぶかを確認しました。  
特に BDASpecial-IT35 は、アプリケーションローカルの `WinSCard.dll` で特殊なカード通信を WinSCard API へ見せる構成を理解する資料になりました。  

既存実装は動作実績を持ちますが、個々のコードを品質の基準とはしませんでした。  
呼び出し側が期待する API、保存するリーダー名、再接続の条件を確認し、メモリ所有権、ハンドル寿命、キャンセル、エラー値は Windows の契約と現行コードから組み立て直しました。  

## 基本構成の決定

### DriverHost_PX4 がカードを所有する理由

内蔵カードリーダーは、チューナーと同じ USB デバイス、基板電源、GPIO、UART を使います。  
各 `WinSCard.dll` や各アプリケーションが USB 機器を直接開くと、BonDriver とカード処理が別々に同じ機器を所有し、電源参照、ホットプラグ、複数チューナーの調停が崩れます。  

そこで、USB 機器をすでに一元管理している DriverHost_PX4 にカードサーバーを追加しました。  
機種別のカード操作は `DeviceBase` 派生クラスへ置き、ATR と T=1 は `SmartCard`、共有接続とトランザクションはカードサーバー、WinSCard API の公開は WinSCard_PX4 が担当します。  
責務の現在の境界は [`WinSCard_PX4/README.md`](../winusb/src/WinSCard_PX4/README.md) を参照してください。  

カードサーバーは制御サーバーと TS ストリームサーバーから独立させました。  
カード機能の初期化や名前付きパイプ作成が失敗しても、従来の TS 受信を巻き添えにして DriverHost_PX4 全体を終了させないためです。  

### アプリケーションローカル DLL を選んだ理由

Windows から通常の PC/SC リーダーとしてシステム全体へ登録する方法は、利用者から見れば最も自然です。  
ただし、その実現にはカーネルドライバまたは常駐サービス、インストーラー、署名、ログオン前を含むプロセス寿命の設計が必要で、ポータブルな TVTest や EDCB の運用から離れます。  

本実装の対象は、DTV アプリケーションの実行ファイルと同じディレクトリに置く `WinSCard.dll` です。  
Windows の DLL 検索順を使って WinSCard API を提供し、内蔵カードリーダーへの要求だけを DriverHost_PX4 の名前付きパイプへ送ります。  
ファイルを配置したアプリケーションだけへ影響を限定でき、既存の BonDriver と同じ配布単位で持ち運べます。  

この選択によって、内蔵カードリーダーは Windows のデバイスマネージャーへ通常のスマートカードリーダーとして登録されません。  
これは未完成の結果ではなく、インストール不要とアプリケーション単位の適用を優先した設計上の境界です。  

### WinSCard API を全て公開する理由

初期要件では、DTV ソフトウェアによって利用する WinSCard API が異なるため、一部関数だけを実装した DLL では互換性を維持できないという前提を置きました。  
そのため、System32 と SysWOW64 の `WinSCard.dll` が公開する関数名と ordinal を比較し、同じエクスポートを持つことを必須にしました。  

内蔵カードリーダーへ意味のない関数も、未実装として削除する対象にはしていません。  
内蔵側との統合が必要な API は WinSCard_PX4 が結果を合成し、それ以外は System32 の実装へ転送します。  
この構成により、Windows 固有の入力検査、ANSI 変換、メモリ割り当て、エラー値を独自コードで複製する範囲を抑えています。  

ファイル名が `unsupported.cpp` だった時期には、実装済み API まで未対応に見える問題がありました。  
正式公開前だったため、不要な名前の互換性を残さず `management.cpp` へ改名し、API 管理処理であることが分かる構成へ修正しました。  

## 外付けカードリーダーとの統合

### 内蔵専用 DLL からの拡張

最初の内蔵カードリーダー対応だけでは、アプリケーションローカルの `WinSCard.dll` を配置した時点で、System32 が管理する外付けカードリーダーが見えなくなります。  
物理スロットの接触問題を避けたい利用者や、既存の SCR33xx 系を使う利用者にとって、これは機能の後退です。  

そこで `3af1a8b03fa1f9ca33d6db5e48e8e024f9b8308e` で、System32 の `WinSCard.dll` を後段の実装として読み込むプロキシ機能を追加しました。  
列挙結果は内蔵カードリーダーを先に、外付けカードリーダーを後に固定しています。  
WinSCard_PX4 を配置する行為自体を内蔵カードリーダー利用の意思として扱うため、優先順を変更する設定ファイルは追加していません。  

libaribb25 のように利用可能なリーダーを順に試す呼び出し側では、カードが入った内蔵リーダーを優先し、使えなければ外付けへ進めます。  
外付けリーダーだけを扱う要求は DriverHost_PX4 を起動せず、System32 側だけで完結する構成にしました。  

### RDP で生じる副次的な違い

内蔵カードリーダーは WinSCard_PX4 から名前付きパイプ、DriverHost_PX4、WinUSB、IT930x UART へ進みます。  
この通信は Windows の PC/SC リソースマネージャーを通らないため、リモートデスクトップのスマートカードリダイレクトを受けません。  

外付けカードリーダーは System32 の `WinSCard.dll` へ転送するため、リモートデスクトップセッションの設定に従います。  
WinSCard_PX4 の配置だけで外付けリーダーのリダイレクトを停止することはできず、接続元 PC のリーダーだけが見える場合があります。  
正規の設定方法と利用者向けの説明は、リポジトリ直下の [`README.md`](../README.md) に記載しています。  

## リーダー名と個体識別

複数台の同型機を接続した場合、列挙順の `#1` や `#2` を名前に使うと、USB の抜き差しや起動順で別の物理カードを指す可能性があります。  
有料契約を結び付けたカードを明示選択する用途では、保存済みのリーダー名が別個体へ移る挙動を避ける必要があります。  

一方、デバイスパスや USB VID、PID をそのまま表示すると、日常的に見る名前として読みにくくなります。  
最終的に、機種名へデバイスインターフェースパス由来の16桁 ID を `(ID: ...)` の形で加え、人間向けの短さと個体の安定性を両立しました。  
現在の生成規則とポート変更時の制約は [`WinSCard_PX4/README.md`](../winusb/src/WinSCard_PX4/README.md) に記載しています。  

この名称は正式公開前に決めたため、途中実装の `#16桁` を内部互換名として残す案は採用しませんでした。  
未公開の名前へ互換レイヤーを追加すると、表示名と内部識別の二重管理だけが長く残るためです。  

## WinSCard 層へ持ち込まなかった処理

内蔵スロットが放送用 CAS カードを想定していても、WinSCard API 層が B-CAS の契約判定や ECM 処理を担当する必要はありません。  
復号処理は TvCas や libaribb25、カード通信は WinSCard API という境界を維持しました。  

開発用の `bcas_atr.hpp` は、外付けカードリーダーへ試験用 B-CAS APDU を誤送信しないための判定材料です。  
複数の ATR を仮想カード名へ登録し、`SCardLocateCards*()` で B-CAS 固有の結果を返す初期案は削除しました。  
カード名を要求する API は System32 のカードデータベースへ委ね、内蔵リーダーはリーダーとカードの状態だけを公開します。  

B-CAS の ATR 末尾が個体ごとの乱数であるという扱いもしていません。  
Windows 検証環境と既存実装で確認した複数の ATR は固定形式として試験に使いますが、製品コードで許可一覧にせず、ATR 自体の長さ、TCK、インターフェースバイトを解析します。  

## 状態管理へ置いた重点

カードの抜去、再挿入、USB 切断、T=1 の送受信連番、ATR の残留バイト、WTX、複数クライアントの共有は、相互に独立した問題ではありません。  
1つの状態だけを無効にすると、別カードへ古い ATR や連番を適用し、数時間後に復号が止まる可能性があります。  

そのため、通信失敗後はセッションを一括破棄し、次の要求でカード検出とリセットから再構築する形にしました。  
共有接続と排他接続、トランザクションはカードサーバーで直列化し、名前付きパイプ接続が切れた場合も所有数を回収します。  
詳細な状態遷移は恒久仕様の README と自動試験へ置いてあり、この歴史文書では繰り返しません。  

チューナーを開いていない間もカードだけを利用できることは、明示的な要件でした。  
カード接続も基板電源の利用者として数え、カード利用中に最後のチューナーを閉じても電源を止めません。  
逆に、受信中にカード接続が閉じても、チューナーが残っている限り電源を維持します。  

## 採用しなかった案

### システム全体の PC/SC ドライバ

通常のスマートカードリーダーとして Windows へ登録する案は、利用者にとって分かりやすい利点があります。  
ただし、常駐寿命、インストール、署名、更新、サービス空間とユーザー空間の境界が必要になり、本実装が前提とするポータブル配布から大きく外れるため採用しませんでした。  

### 内蔵リーダーだけを公開する DLL

実装量は減りますが、外付けカードリーダーを隠し、障害時の代替手段も失います。  
System32 の実装を後段へ接続する方が、互換 DLL を置いたアプリケーションの選択肢を維持できます。  

### 優先順を指定する設定ファイル

内蔵リーダーを使うために DLL を置いたのに、外付けが先頭へ来る初期値は利用者の意図と合いません。  
内蔵を先、外付けを後に固定すれば自動選択する既存ソフトウェアでも目的を満たせるため、設定項目は増やしませんでした。  

### 先行フォークの状態機械をそのまま移植する案

通信可能性は実証されていましたが、分割受信、完全性検証、再送、WTX、ホットプラグ、複数リーダーの条件が不足していました。  
低水準コマンドだけを参照し、Windows 側の所有権と模擬 I/O 試験に合わせて作り直しました。  

### 保存済み TS だけを使う性能確認

保存済み TS の一括復号は、カードが APDU へ応答できることを確認できます。  
実際の受信と同じ USB ブリッジ上で TS と UART が同時に動く条件や、放送速度へ継続して追従する性能は測れません。  
最終的な判定には BonDriver のライブ TS をその場で復号する試験を採用しました。  

### 実行ファイルへの自己署名

配布処理の検討中に、BonDriver、DriverHost_PX4、WinSCard_PX4 へ自己署名を付ける変更が入りました。  
自己署名証明書を信頼済みルートへ入れても Smart App Control 対応にはならず、ポータブルな実行ファイルの利用条件だけを増やすため、`9d2c86dd4239096a220d22e9bf07893e5eda9d07` で削除しました。  
自己署名は WinUSB ドライバーパッケージのカタログ署名に限定しています。  

## 実装のまとまり

初期実装は、既存機能への影響を追いやすくするため、役割ごとにコミットを分けました。  
主要なまとまりは次のとおりです。  

- `f4f59d0`: Linux と WinUSB から共有する IT930x の B-CAS 低水準コマンド
- `40e8eb7`: ATR と T=1 の状態機械、および模擬デバイス試験
- `99e35b6`: DriverHost_PX4 のカードサーバーと機種別カード操作
- `bec0aa8`: アプリケーションローカルの WinSCard_PX4 と API 試験
- `02902e1`: TS とカードを同時に動かす実機試験ツール
- `44e99cb`: ビルドと配布物への組み込み
- `3af1a8b`: System32 の外付けカードリーダーとの共存
- `706f604`: WinSCard API の細部と接続処理の見直し
- `5969a51`: 安定した個体 ID を含むリーダー名
- `d4b98d0` と `e26b12b`: 製品情報と版番号の共通管理

この分割は、履歴を見やすくするためだけのものではありません。  
将来の修正で、低水準コマンド、T=1、DriverHost_PX4、WinSCard API、試験、配布処理を一括変更しないための境界でもあります。  

## メンテナの判断から残す原則

メンテナが一貫して求めたのは、理論上の完全性を増やすことより、実際の DTV 利用で必要な挙動を小さく正しく実装することでした。  
互換性が必要な公開 API は省略せず、クライアントが要求していない B-CAS 固有データベース、設定項目、署名処理は増やさないという判断です。  

正式公開前の途中仕様へ互換性を作り、内部名と表示名を二重に維持することも避けました。  
互換性は実際の利用者と公開済み契約を守るためのものであり、未公開の試作を残す理由にはなりません。  

ドキュメントでは、利用者が何を配置し、どのリーダーが見え、どの条件で使えるかを先に書くことが求められました。  
証明書の信頼モデルや実装上の抽象化は、それが利用条件を変える場合に限って説明します。  
後続作業でも、技術的に可能な構成を増やす前に、利用者の操作と長時間録画へ何が変わるかを確認してください。
