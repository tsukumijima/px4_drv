# WinSCard_PX4 設計資料

この文書は、WinSCard_PX4 を保守する開発者に向けて、実装の目的、責務の境界、壊してはいけない条件、検証方法を記録したものです。  
利用者向けの導入手順はリポジトリルートの [README.md](../../../README.md) を参照してください。

## 解決する問題

px4_drv が扱う PLEX 製品と e-Better 製品の内蔵カードリーダーは、独立した USB PC/SC デバイスとして接続されていません。  
カードとの通信は、IT930x 系 USB ブリッジを介して UART と制御コマンドを送受信する構造になっています。  
このため、WinUSB 版ドライバを導入しただけでは Windows のスマートカードリソースマネージャーから内蔵カードリーダーを列挙できません。

**WinSCard_PX4** は、DTV アプリケーションと同じディレクトリへ `WinSCard.dll` として配置し、Windows WinSCard API に内蔵カードリーダーを追加する互換 DLL です。  
互換 DLL という配置方法は、TVTest や EDCB のポータブルな運用を保ち、システム全体へのドライバ登録や常駐サービスの追加を避けるために選択されています。

## 守るべき要件

WinSCard_PX4 の変更では、次の要件を同時に満たす必要があります。

- 内蔵カードリーダーを Windows WinSCard API と同じ呼び出し方で利用できる
- 内蔵カードリーダーを列挙順の先頭に置き、その後へ Windows が管理する外付けカードリーダーを追加する
- `WinSCard.dll` を配置した状態でも、SCR3310 系などの外付けカードリーダーを利用できる
- 内蔵カードリーダーを使わない処理は、原則として System32 の `WinSCard.dll` と同じ結果を返す
- 32bit アプリケーションと 64bit アプリケーションの双方で同じ API 契約を保つ
- チューナーを開いていない機器の内蔵カードリーダーも利用できる
- 受信に使うチューナーと、復号に使う内蔵カードリーダーが別の機器にあっても動作する
- 1枚のカードを複数の受信処理が共有する場合も、カード上の T=1 通信を直列化する
- カード通信の追加や失敗が、TS 受信経路を停止させたりドロップを発生させたりしない
- 抜去、再挿入、USB 切断、通信タイムアウトの後に、以前のカードの ATR や T=1 連番を再利用しない

このうち、TS 受信を壊さないことが最優先です。  
内蔵カードリーダー機能の起動に失敗した場合も、既存の BonDriver と DriverHost_PX4 による受信機能は継続できなければなりません。

## 構成

WinSCard_PX4 は単独でハードウェアを操作せず、DriverHost_PX4 のカードサーバーへ要求を送ります。

```text
DTV アプリケーション
    |
    | WinSCard API
    v
WinSCard_PX4 (WinSCard.dll)
    |                         |
    | 内蔵リーダー            | 外付けリーダーと Windows 管理 API
    v                         v
名前付きパイプ              System32 の WinSCard.dll
    |
    v
DriverHost_PX4 / CardServer
    |
    v
SmartCard / CardDevice
    |
    v
機種別デバイス実装
    |
    v
IT930x 制御転送と UART
```

この分離により、アプリケーションごとの WinSCard API 互換処理、プロセス間通信、T=1 プロトコル、機種固有の電源管理を別々に検証できます。

### WinSCard_PX4 側

[`winscard.cpp`](winscard.cpp) は、コンテキストとカードハンドルの管理、内蔵カードリーダーと外付けカードリーダーの振り分け、列挙、接続、状態監視、通信、キャンセルを担当します。

[`management.cpp`](management.cpp) は、カード種別データベースの照会と管理、カードの検索、リーダーの機器情報、キャッシュなどの WinSCard API を扱います。  
内蔵カードリーダーとの統合が必要な関数だけ PX4 側の結果を加え、その他の関数は System32 側へ転送します。

[`native_winscard.cpp`](native_winscard.cpp) は、Windows のシステムディレクトリを明示して本物の `WinSCard.dll` をロードします。  
相対パスや通常の DLL 探索順を使うと WinSCard_PX4 自身を再帰的にロードするため、絶対パスによるロードを維持してください。

[`proxy_support.hpp`](proxy_support.hpp) は、ANSI 文字列と Unicode 文字列の変換、出力バッファのサイズ契約、`SCARD_AUTOALLOCATE`、`SCardFreeMemory()` の所有権を扱います。

[`card_client.cpp`](card_client.cpp) は、DriverHost_PX4 の探索と起動、名前付きパイプへの接続、固定長コマンドの送受信を担当します。  
名前付きパイプの接続成功を DriverHost_PX4 の起動完了条件としているのは、プロセスの生成成功だけでは要求を受け付けられる状態と限らないためです。

[`exports.def`](exports.def) は DLL の公開 API 契約です。  
エクスポートする関数名と ordinal は、同じアーキテクチャの System32 または SysWOW64 にある `WinSCard.dll` と一致させる必要があります。

### DriverHost_PX4 側

[`../DriverHost_PX4/card_server.cpp`](../DriverHost_PX4/card_server.cpp) は、リーダー列挙、接続の共有条件、トランザクション、カード単位の排他制御を担当します。

[`../common/card_command.hpp`](../common/card_command.hpp) は WinSCard_PX4 と DriverHost_PX4 のプロセス間通信契約です。  
コマンド構造体は固定長であり、文字列の終端、配列の長さ、プロトコル版を受信側で検証します。  
構造体を変更する場合は、古い DLL と新しい DriverHost_PX4 が混在したときの挙動を明示し、`card_command::VERSION` を更新してください。

[`../DriverHost_PX4/smart_card.cpp`](../DriverHost_PX4/smart_card.cpp) は、カードの検出、ATR の取得と解析、T=1 の初期化、APDU の分割と連結、再送、状態破棄を担当します。  
[`../DriverHost_PX4/card_device.hpp`](../DriverHost_PX4/card_device.hpp) は、T=1 処理から機種固有の UART 操作を隔離する抽象インターフェースです。  
各機種の `DeviceBase` 派生クラスは、カードリーダーの有無、電源の参照数、USB 切断時の無効化を実装します。

## WinSCard API の互換性

WinSCard_PX4 は、B-CAS 専用 API を新設する層ではありません。  
アプリケーションから見える契約は WinSCard API のままにし、B-CAS の ECM 処理や契約判定は TvCas や libaribb25 などの上位層へ残します。  
ハードウェアは放送用 CAS カードの利用を前提としており、現在の通信初期化は B-CAS と ACAS の B-CAS 互換機能を扱います。  
この機器側の制約を仮想カード種別データベースとして WinSCard API へ持ち込まないでください。

[`bcas_atr.hpp`](bcas_atr.hpp) の ATR は、実機試験で外付けカードへ B-CAS 固有 APDU を誤送信しないための判定材料です。  
製品コードのリーダー列挙や `SCardLocateCards*()` が、この ATR 一覧をカード種別データベースとして利用する設計にはなっていません。

### 転送の原則

内蔵カードリーダーとの統合を必要としない API は System32 側へそのまま転送します。  
列挙結果や状態配列に内蔵カードリーダーが含まれる場合だけ、PX4 側の結果と System32 側の結果を統合します。  
この境界を広げるほど、Windows が持つ細かな入力検証、エラーコード、メモリ割り当ての挙動を複製する範囲が増えます。

新しい処理を加える前に、System32 への単純転送で契約を満たせない理由を確認してください。

### ANSI と Unicode

WinSCard API の `A` 版と `W` 版は、単なる別名として扱えない関数があります。  
外付けカードリーダーだけを扱う ANSI API は、可能な限り System32 の ANSI API へ転送し、Windows と同じコードページ変換とエラーを保ちます。  
PX4 側と結果を統合するときだけ、明示的に文字列を変換します。

### 出力バッファ

WinSCard API は、呼び出し元が用意したバッファ、必要長だけを問い合わせる呼び出し、`SCARD_AUTOALLOCATE` の3形式を持ちます。  
成功時と `SCARD_E_INSUFFICIENT_BUFFER` 時の長さ、文字列の終端、`MULTI_SZ` の二重終端を Windows と同じ単位で返してください。

WinSCard_PX4 が割り当てたメモリと System32 が割り当てたメモリは、割り当て元を記録して `SCardFreeMemory()` を正しい実装へ振り分けます。  
割り当て元の追跡を省くと、別のヒープへ解放を要求するため、長時間運用で破損を招きます。

### コンテキストとカードハンドル

内蔵カードリーダーと外付けカードリーダーのハンドルは、WinSCard_PX4 が管理するハンドルへ包んで呼び出し元へ返します。  
公開ハンドルからバックエンドの種類を推測させず、内部のコンテキスト表とカード表を唯一の対応関係として扱います。

コンテキスト解放時は、そのコンテキストに属するカードを閉じ、待機処理を解除してからバックエンドのコンテキストを解放します。  
接続処理とコンテキスト解放が競合しても、表へ登録されないカードハンドルを残してはいけません。

### キャンセル

PX4 側の状態待機は、コンテキストごとのキャンセル世代を使って解除します。  
System32 側の `SCardCancel()` は、そのコンテキストで System32 の待機 API が実際に進行している間だけ呼び出します。  
待機していないコンテキストへ不要な `SCardCancel()` を送ると、次の外付けカードリーダー操作までキャンセル状態を引き継ぐ実装があるためです。

## 列挙順と機器の識別

`SCardListReaders*()` は、DriverHost_PX4 が列挙した内蔵カードリーダーを先に返し、System32 が列挙した外付けカードリーダーを後へ追加します。  
互換 DLL を配置する行為は内蔵カードリーダーを使う意思を示すため、この順序は設定項目にせず固定しています。  
libaribb25 のように先頭の利用可能なリーダーを選ぶ実装では、カードが挿入された内蔵カードリーダーが優先され、利用できなければ後続の外付けカードリーダーを試せます。

内蔵カードリーダー名の `(ID: ...)` には、Windows のデバイスインターフェースパス全体から生成した16桁の ID を使います。  
USB VID や PID はそのまま表示せず、`PLEX PX-W3U4 Smart Card Reader (ID: CD65353E4231AA77)` のように、利用者が同じ機種の複数個体を見分けられる名前にしています。  
ID の生成には64bit FNV-1a を基にしたハッシュを使い、機種情報と個体情報を含むパス全体を入力します。  
異なる機種で同じシリアル番号が使われていても入力は別になり、通常は異なる ID を生成しますが、64bit の有限な値なので理論上のハッシュ衝突は残ります。  
シリアル番号を持たない機器では接続先の USB ポートがデバイスパスに使われる場合があり、USB ポートを変更すると ID も変わる可能性があります。  

DriverHost_PX4 はカードリーダー一覧の世代番号を持ち、対応機器の追加と削除で更新します。  
WinSCard_PX4 は世代の変化を使ってホットプラグを検出し、`SCardGetStatusChange*()` の待機を解除します。  
同名の機器が再接続された場合も、古い `DeviceBase` を新しい機器へ流用せず、新しい共有カード状態を作ります。

## DriverHost_PX4 の寿命

WinSCard_PX4 は、同じディレクトリまたは BonDriver 用サブディレクトリから DriverHost_PX4 を探索します。  
名前付きパイプが存在しない場合は DriverHost_PX4 を非表示で起動し、接続可能になるまで絶対期限の範囲で待ちます。

DriverHost_PX4 は多重起動をグローバルミューテックスで防ぎます。  
制御、TS ストリーム、カードの各サーバーが連続してアイドル状態になったことを確認してから終了します。  
状態監視やカード接続が続いている間は、チューナーが開かれていなくてもカードサーバーが DriverHost_PX4 の寿命を保持します。

カードサーバーの開始に失敗した場合はログへ残した上で、既存の制御サーバーと TS ストリームサーバーはそのまま動き続けます。

## カードの共有と排他制御

DriverHost_PX4 は、カードリーダー名ごとに `SharedCard` を共有します。  
`SharedCard` は `SmartCard`、カード単位の再帰ミューテックス、共有接続数、排他接続数を保持します。

`SCARD_SHARE_SHARED` は複数接続を許し、`SCARD_SHARE_EXCLUSIVE` は他の接続がない場合だけ許します。  
各 APDU とカード状態の変更はカード単位で直列化し、複数クライアントが同じ T=1 連番を同時に進めないようにします。

`SCardBeginTransaction()` から `SCardEndTransaction()` までの所有権は名前付きパイプ接続ごとに記録します。  
クライアントが異常終了しても、接続の破棄時にトランザクションと共有数を必ず解放します。  
`SCardEndTransaction()` の disposition 処理が失敗した場合も、ミューテックスの所有権だけは解放します。

## カード状態の管理

`SmartCard` は、UART が開いている状態、カードの存在、T=1 初期化の完了、ATR、IFSC、EDC 種別、送受信連番を保持します。  
カードが入っていない状態でも UART を開いたまま待機できるため、後から挿入されたカードを状態監視で検出できます。

抜去、USB 切断、通信エラー、プロトコル違反、タイムアウトを検出した場合は `InvalidateSession()` を呼びます。  
この処理は ATR、IFSC、CRC 設定、T=1 の送受信連番をすべて初期値へ戻します。  
次の APDU はカードの再検出とリセットから始まるため、壊れたセッションの続きが送られることはありません。

TVTest などの上位アプリケーションがカード接続や復号器を保持する場合、物理的な再挿入だけでは復号が再開されないことがあります。  
ドライバ側は再挿入を検出して新しいセッションを開始できますが、上位層が再接続や ECM の再処理を行うかどうかは別の状態管理です。

## ATR と T=1

ATR は受信済みバイト数だけで完了と判断せず、インターフェースバイト、履歴バイト、TCK を解析して期待長を求めます。  
T=1 の IFSC と EDC 種別は、T=1 を示す `TD2` の次のグループにある `TA3` と `TC3` から取得します。  
T=0 固有の `TC2` や特定モードを示す `TA2` を T=1 の値として解釈してはいけません。

一部の実機では連続リセット時に UART の残留バイトが ATR より先に返ることが確認されています。  
形式不正の ATR に限って1回だけカードを再リセットし、再試行前に ATR 解析状態を初期化します。  
タイムアウトや USB エラーを同じ再試行へ含めると、切断や接触不良を長時間隠すため、対象を広げないでください。

B-CAS は ATR の TA1 に従って19200bpsへ切り替え、RESYNCH と IFS 要求で T=1 を初期化します。  
ACAS は TA1 の `0x13` に従って38400bpsへ切り替え、IFS 要求から初期化を始めます。  
ACAS が最初の IFS 要求へ応答しない場合に限り、同じ絶対期限内で RESYNCH と IFS 要求を1回再実行します。

カードが通知した IFSC と UART の255バイト上限の小さい方に従って APDU を I ブロックへ分割し、受信可能な INF の最大長を IFSD としてカードへ通知します。  
ACAS が IFSC 254を通知した場合も、LRC では251バイト、CRC では250バイトを1ブロックの上限とし、残りを次の I ブロックへ送ります。  
LRC と CRC の双方を扱い、CRC は T=1 の送受信形式に合わせて上位バイトから並べます。

## タイムアウトと再送

カード通信の期限は、待機処理を呼ぶたびに作り直さず、1回の ATR 取得または APDU 送信の開始時に絶対時刻として決めます。  
T=1 の WTX 要求へは正しく応答しますが、APDU 全体の期限は延長されません。  
カードや壊れた通信相手が WTX を繰り返しても、DriverHost_PX4 のスレッドを無期限に占有させないためです。

ブロック受信の短いタイムアウトは再送へ進む条件であり、APDU 全体の期限は再送を含む上限です。  
期限切れや再送失敗の後はセッションを破棄し、次の APDU でカードを再初期化します。  
タイムアウト値を変更する場合は、カード単体の試験に加え、同じ USB ブリッジで TS 受信と UART 通信が同時に進む条件を測定してください。

## TS 受信との分離

カード通信は IT930x の制御転送を使うため、同じ USB ブリッジの TS 受信と物理資源を共有します。  
特に ISDB2056 系では、録画済み TS を後から復号する試験だけでは、リアルタイム受信時の競合を再現できません。  
カード単体試験の成功を、受信中の安定性の証拠として扱わないでください。

カード用のロックを TS 受信バッファのロックと共有したり、カード応答待ちの間に受信経路のロックを保持したりしてはいけません。  
機種別実装が USB 制御転送を直列化する必要がある場合も、待機時間とロック範囲を実機の同時受信試験で確認します。

## 外付けカードリーダーとの共存

外付けカードリーダーだけを扱う呼び出しは、WinSCard_PX4 が DriverHost_PX4 を必要としない条件でも完結します。  
この条件は、DriverHost_PX4 を配置しない隔離ディレクトリで試験してください。

外付けカードリーダーのリアルタイム試験では、BonDriver による受信中に System32 側のカードへ APDU を送り、復号後のスクランブルパケット数と処理時間を測定します。  
保存済み TS の一括復号だけでは、受信速度へ追従できることを確認できません。

System32 側の戻り値を PX4 側のエラーへ一律に変換せず、外付けカードリーダーの呼び出しでは Windows のエラーを維持してください。

リモートデスクトップ接続中も、内蔵カードリーダーは名前付きパイプから DriverHost_PX4 と WinUSB へ進むため、Windows のスマートカードリダイレクトを通りません。  
外付けカードリーダーは System32 の `WinSCard.dll` へ転送されるため、呼び出したリモートデスクトップセッションのリダイレクト設定に従います。  
WinSCard_PX4 を配置しても外付けカードリーダーのリダイレクトは無効にならず、接続元 PC のリーダーだけが見える場合があります。  
利用者向けの設定方法は、リポジトリ直下の [`README.md`](../../../README.md) に記載します。

## 機種差

カードリーダーの有無は、製品名の文字列から呼び出し側が推測せず、各 `DeviceBase` 派生クラスの `HasCardReader()` を基準にします。  
カードリーダーを持たない機種では、公開されたカード操作の入口で拒否し、UART の初期化や GPIO 読み取りには進みません。

PX-MLT8PE は1台の筐体に5チューナー側と3チューナー側のデバイスが入った構成です。  
コード上の `PXMLT8PE3` は3チューナー側を識別する名前であり、独立した市販製品名として扱わないでください。

共有電源を持つ機種では、チューナー利用数とカード利用数を同じ電源状態へ反映します。  
チューナーを閉じてもカード接続が残っている間は電源を維持し、USB 切断時はカード状態と電源の参照を同時に破棄します。

## 検証

`winusb/build.ps1` を実行すると、Visual Studio 2022 の MSBuild を使い、x86 と x64 の両方のアーキテクチャで `Release-static` ビルドが生成されます。  

```powershell
# リポジトリルートから実行する
Set-Location winusb
.\build.ps1
```

### 実機に依存しない試験

- `smart_card_state_test`: 抜去、再挿入、ATR 解析、B-CAS と ACAS の初期化、APDU 分割、CRC、再送、WTX、期限切れ、セッション破棄を模擬デバイスで検証
- `ts_sync_condition_test`: 通常 TS と受信機番号付き TS の同期判定を実行値で検証
- `winscard_api_test`: 列挙、接続、状態、メモリ所有権、ANSI と Unicode の API を検証
- エクスポート比較: System32 と SysWOW64 の `WinSCard.dll` に対して関数名と ordinal の双方を確認

### 実機試験

- 内蔵カードリーダー単体で ATR を取得し、B-CAS APDU の応答を確認
- 対応する全機種について、カードの挿入と未挿入、USB の抜去と再接続を確認
- 複数クライアントから同じカードへ接続し、共有接続とトランザクションの動作を確認
- 内蔵カードリーダーを使いながら同じ機器で TS をリアルタイム受信し、ドロップ、同期エラー、連続性エラー、スクランブルパケットを測定
- 1枚のカードで複数チューナーを同時受信し、復号処理が放送速度へ継続して追従することを確認
- DriverHost_PX4 が存在しない環境で外付けカードリーダーだけを列挙、接続、復号できることを確認
- 内蔵カードリーダーと外付けカードリーダーを同時に接続し、列挙順と明示選択の双方を確認

受信試験では、TVTest の画面だけで判定せず、D、E、S の計数、APDU の失敗数、処理時間を記録してください。

## 変更時の確認項目

WinSCard_PX4 またはカードサーバーを変更した場合は、少なくとも次の項目を確認します。

- System32 と SysWOW64 の全エクスポートに欠落がない
- `A` 版と `W` 版で入力検証、長さ、エラーコードが対応している
- `SCARD_AUTOALLOCATE` と `SCardFreeMemory()` の割り当て元が対応している
- 内蔵カードリーダーを含まない呼び出しが System32 側だけで完結する
- 内蔵カードリーダーの列挙順が外付けカードリーダーより前にある
- 状態待機のキャンセルが別の接続や次回の接続を汚染しない
- コンテキスト解放と接続が競合してもハンドルが残らない
- クライアントの異常終了後に共有数とトランザクションが残らない
- USB 切断後の操作が `SCARD_E_READER_UNAVAILABLE` 相当で失敗し、古いセッションを使わない
- WTX と再送が続いても APDU 全体の期限を超えない
- カード通信中の TS 受信にドロップ、同期エラー、連続性エラーが増えない
- x86 と x64 の両方をビルドし、同じ試験を実行している

## 採用しなかった構成

Windows のスマートカードリーダードライバとしてシステムへ登録する構成は、標準の WinSCard API から自然に利用できる利点があります。  
ただし、カーネルドライバまたはシステムサービス、インストーラー、コード署名、非ログイン状態を含む常駐寿命の設計が必要になります。  
ポータブルな DTV アプリケーションへファイルを配置する既存運用との隔たりが大きいため、現在はアプリケーションローカルの互換 DLL を採用しています。

内蔵カードリーダーだけを公開する互換 DLL は実装が短くなりますが、同じアプリケーションから外付けカードリーダーを使えなくします。  
利用者が物理的な接触不良や機種差を回避できるよう、System32 側のプロキシ機能を含めています。

リーダー名の優先順を設定ファイルで変更する構成も見送りました。  
WinSCard_PX4 を配置した利用者の意図と、自動選択する既存ソフトウェアの挙動を一致させるため、内蔵リーダーを先頭に固定しています。

## Linux 版への引き継ぎ

yyya-nico 氏のフォークは、IT930x の UART と GPIO を使って Linux から内蔵カードへ通信できることを示しています。  
ベンダー由来の `it930x_driver_native` と併せて、レジスタ、制御コマンド、極性、ボーレートを確認する資料として利用できます。

一方、確認したフォークの `px4_card.c` には、ATR を3バイト以上で完了扱いする簡易判定、`read()` で出力先のユーザーバッファから構造体を読み込む特殊な契約、T=1 セッション全体の状態管理を利用者側へ委ねる構造が含まれます。  
このため、通信手順の実証コードとして参照し、公開 API と状態管理をそのまま本家へ移植しない方針が適切です。

Linux 版では、次の知見を維持した上でカーネルの寿命管理に合わせて再設計してください。

- USB デバイスの切断後に、開かれているファイルと非同期処理が解放済みのデバイスへ触れない参照管理を実装
- カードの開閉、電源参照、チューナー利用数を機種ごとに一貫したロックで管理
- GPIO の入力設定など初期化時に1回で済む制御転送を、カード検出のポーリングごとに繰り返さない
- ATR の期待長と TCK を解析し、受信済みバイト数だけで完了扱いしない
- T=1 の状態機械は送受信連番、I ブロックの連結、R ブロックの再送、S ブロック、IFSC、EDC を明示的に保持
- ATR 取得と APDU 送信に絶対期限を設け、WTX や再送で無期限に延長しない
- 通信失敗後は T=1 セッションを破棄し、次回の要求でカードをリセット
- カードの抜去と再挿入を状態変化として通知し、古い ATR と連番を次のカードへ渡さない
- 同じカードを利用する複数プロセスの共有条件とトランザクションを公開 API で定義
- TS 受信とカード UART 通信を同じ USB ブリッジで同時に実行する試験を用意
- プロトコル処理をハードウェア操作から分離し、模擬デバイスで状態遷移と期限を自動試験

Linux 側の公開方法は、PC/SC の IFD Handler、専用の文字デバイス、ユーザー空間デーモンなど複数の構成が考えられます。  
この文書は公開 API を先に固定せず、上記の寿命、排他、期限、回復の条件を満たすことを求めます。

## 確認済みの範囲と残る不確実性

開発時の実機確認では、DTV02A-1T1S-U の ISDB2056、PX-MLT5PE、PX-W3U4 の内蔵カードリーダーで ATR と APDU を確認しています。  
SCR33xx 系の外付けカードリーダーについても、内蔵カードリーダーとの同時列挙と外付け単独のリアルタイム復号を確認しています。

コード上は他の対応機種にもカード操作を実装していますが、全機種の全ロットを実機で確認したことを意味しません。  
ACAS の ATR、初期化順序、ブロック待機時間、UART 上限での APDU 分割は模擬デバイスで確認していますが、Windows 上の ACAS 実カードでは確認していません。  
リモートデスクトップ接続時の経路はコードと Windows の仕様から確認しており、実際のリモートデスクトップセッションでは試験していません。  
長時間の連続録画、USB の瞬断、アプリケーション固有の再接続、まれな T=1 エラーには未確認の組み合わせが残る可能性があります。  
既存の動作実績を理由にエッジケースを否定せず、再現条件を計測してから小さな変更と自動試験で修正してください。
